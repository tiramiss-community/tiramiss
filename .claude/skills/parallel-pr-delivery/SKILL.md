# 並行PR作業

## 担当を一本化する

- 取りまとめは1人。現在の親が担当できるなら調整専用の子を作らない。取りまとめ役に指定されたモデルが親と異なる場合だけ、そのモデルの子を唯一の取りまとめ役にし、親は利用者への連絡に専念する。同じ調査・判断・監視を両者で繰り返さない。
- 利用者指定のモデル・並列数を優先する。指定がなければ既定モデルを使う。並列数は実際の利用枠と独立性で決め、枠を埋めるための分割はしない。
- 現在のIssue・先行依存・open PR・完了条件を確認し、製品ファイルだけでなく共有の台帳・比較記録・生成物・依存環境の編集者も決める。独立PRは同じ統合先を基点とし、stackが必要なら依存理由を示す。
- 作業は専用worktreeへ隔離する。共有node_modulesへのsymlinkを介したinstall/rebuildは隔離ではない。実DB等のプロジェクト名・ポート・片付けの所有者を分ける。

## 小さい引き継ぎで実装する

子への入力は、対象Issueと完了条件、基点/worktree、編集範囲、固定比較元、必要な規約、既知の制約と検証コマンドに絞る。対応するツールではfork_turns=noneを使い、会話全体や巨大なログを渡さない。

実装前に通常の製品入口が完了条件を満たすか、比較元が実際のimport先かを確認する。テストfixtureだけで成立する保証を通常起動の保証に読み替えない。新しい観測のIDは一意にし、入力と結果を1対1で照合する。

報告は「変更/検証結果/未解決/次の判断/成果物のパス」に絞る。全ログはファイルに保存し、親には失敗箇所と必要な周辺だけ渡す。同じ事実を複数担当が報告し直さない。

## 比較記録の保守を分離する

必要な場合だけ、プロジェクトエージェント `evidence_inventory`（Luna）または `evidence_maintainer`（Terra）を使う。定義は現在のworktreeの [evidence_inventory](../../../.codex/agents/evidence_inventory.toml) と [evidence_maintainer](../../../.codex/agents/evidence_maintainer.toml) にある。個人用の同名定義より、このworktree内の定義を参照する。利用クライアントが名前付きエージェントを扱えない場合は、該当TOMLのmodel・reasoning・developer_instructionsを明示して通常の子として起動する。利用できないモデルを黙って置換しない。

小さな更新なら実装担当が行い、調査→保守の2人を毎回起動しない。調査はread-only、保守は指定ファイルだけ。次は取りまとめ役へ戻す:

- 本家との差・完了条件・意図的差異の新しい判断
- validatorの保証、readerの合成、memoization/invalidationの変更
- 検証上限の変更や複数領域へ広がる修正

古い測定値を現在の実装へ付け替えない。hash更新は再測定の代わりにならない。実測入力と後続の記録更新を区別する。

## 独立レビューと検証

- 実装者以外のレビューを必須にする。通常入口・本家参照・失敗境界・証拠の対応を確認する。
- 修正後は変更箇所と影響範囲を再レビューする。無関係な全体レビューを再開しない。基盤契約に波及する変更なら範囲を広げる理由を示す。
- 変更に近いテストとリポジトリ必須チェックを実行する。同じheadの成功を理由なく繰り返さない。新しい変更・失敗・具体的な懸念があるときに追加する。
- 複数PRが共通ファイルを触る場合は最終head同士の競合と必要な合成検証を一度確認する。FAILやSKIPを成功に混ぜない。

## PRと監視の終了条件

PR作成・push・外部送信は現在の依頼が許可する範囲だけ。スキル自体は送信権限を与えない。merge/close/force-pushの権限も追加しない。

監視担当は1人。CIは最新head、Webレビューは対象commit・未解決指摘・処理中の有無を追跡する。通知が使えるなら利用し、なければCIは間隔を置いて確認する。レート制限は次の依頼可能時刻を記録し、解除前に繰り返し送信しない。待機中の新規サブエージェントや調査を増やさない。報告は状態変化中心とし、上位指示が定期報告を要求する場合は短くまとめる。

通常の完了条件:

1. 独立レビュー済みで、最新CIが成功している。
2. 依頼されたWebレビューが一度完了し、指摘を検証して修正または根拠付き返信をした。修正差分は独立確認し、必要な最新検証を通した。
3. 既知の未解決事項・実際に進行中のレビューへ対応した。

修正後すべての差分にWeb再レビューや正式APPROVEDを要求する条件を勝手に追加しない。利用者やリポジトリが要求する場合は従う。追加のWeb再レビューが制限中なら、その事実と実際の確認範囲を明記する。旧CHANGES_REQUESTED表示を承認済みと呼ばない。初回Webレビューが未到達なら完了とは扱わず、許可範囲で待機を続けるか利用者へ阻害要因を伝える。

引き継ぎはPR、変更の目的、最新検証、レビュー状況、残る制限を短く示す。
