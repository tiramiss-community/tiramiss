# 新バックエンドの目的と初期完成条件

この文書は、実装・詳細設計・Issueを判断するための短い基準。目的や初期範囲をユーザーと変更したときだけ更新し、作業ログや個別の設計を増やさない。

## 目的

**本家Misskeyと同等のバックエンドを新しい技術スタックで組み直し、絡み合った依存関係を解きほぐす。**

Hono・InversifyJS・TypeORM・BullMQを使い、業務判断、データ取得・保存、HTTP・非同期実行を分離する。安定性向上や機能拡張は、この境界を使って後から加えられるようにする。

## 初期完成条件

- 対象の本家コミットと同等のAPI・認証/認可・stream・ActivityPub・ジョブ・必要な管理機能が動く。入力/出力だけでなく、エラー・保存結果・副作用・通常の再試行も比較する。
- 本家の既存データとmigration履歴を引き継ぎ、既存クライアントから利用できる。既存fork固有機能は移植対象にしない。
- 業務コードにHono Context・TypeORM EntityManager・BullMQ Job・DIコンテナを持ち込まず、モジュールの公開契約と依存方向を読み解ける。
- 代表フローを新実装だけで通し、対象機能の移植・比較と完全停止下の切り替え検証が揃う。adapterや基盤の存在だけで機能完成としない。

## 初期完成の前提にしないこと

本家以上の配送/復旧保証、独自の永続ジョブ正本・容量課金・物理容量による受付停止、Redis全損からの再構築、厳密な一度だけの副作用成立などを、一律の先行条件にしない。

本家相当の認可・データの整合性・失敗の扱いは維持する。移植や依存整理に必要な変更は行う。本家から挙動・保存方式・必須運用設定を変える場合は、その必要性と負担を別に説明する。

## 判断のしかた

1. この作業が移植する本家機能、または解く依存関係を示す。
2. 新しい保証・永続状態・運用設定を足すなら、本家相当の実装にも必要かを確認する。
3. その追加なしで同等機能と分離を実現できるなら、強化は後続へ分ける。

拡張余地は実際に必要な狭い境界で確保する。将来のためだけの汎用基盤や別実装を先に完成させない。レビューでも、正しさと初期範囲の両方を確認する。

## 作業開始・再開時

本書 → [全体計画](ROADMAP.md) → 対象Issueと必要な設計・実装の順に読む。再開時はブランチ/PRと現在の差分を確認する。

ユーザーの最新指示を最優先にし、詳細設計や過去のレビューだけで本書の目的・初期範囲を拡張しない。通常の実装判断はこの範囲内で進める。過去に承認した差異は理由と履歴を残して再評価し、黙って取り消さない。
