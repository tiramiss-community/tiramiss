# 本家差分台帳とリリース判定

[#135](https://github.com/tiramiss-community/tiramiss/issues/135) の形式・再現例。
判断基準は [GOALS](../GOALS.md)、[基本設計 §16.3](../../superpowers/specs/2026-10-15-misskey-backend-redesign-design.md#163-取り込みと移植の進捗)。
親 [#134](https://github.com/tiramiss-community/tiramiss/issues/134) の移植支援手順は #136 が所有する。
この形式の完成、固定元の機械同期、個別契約の対応、製品全体のリリース許可はそれぞれ別に判定する。

## 記録の単位と保存先

本番の追従ごとにこのディレクトリ配下へ `<旧SHA短縮>-<新SHA短縮>/` を作り、次の3点を保存する。
ここにある `example.json` / `extraction.json` / `verification.md` は固定実差分を使った試行で、現在の全体機能台帳を置換しない。
新旧SHAは本家 `misskey-dev/misskey` の完全な40桁で固定し、forkのHEADと機械同期の固定元SHAも区別する。

| ファイル | 持つ事実 |
| --- | --- |
| `extraction.json` | 全コミットと各第一親との差分path、最終差分path、path→契約ID、抽出漏れレビューの結果 |
| `ledger.json`（例では `example.json`） | 契約ごとの影響・状態・受入条件・実現箇所・検証・判断、前回からの持越し、差分リリース判定 |
| `verification.md` | コマンド、入力の固定元、観測結果・限界。抽出の検査と契約の検証を別節にする |

1コミットに複数契約があれば行を分け、同じ契約の複数コミットは同一行へ対応付ける。ファイル単位だけで完了を決めない。
IDは再利用・削除せず、統合・後続修正・撤回にも元IDと経緯を残す。sourceリンクは本家の完全SHAを使う。
本家の途中コミットだけに存在して最終差分から消えた変更も、理由付きで行へ対応付ける。

## 状態と判断根拠

| 状態 | 必要な根拠 |
| --- | --- |
| 未評価 | 影響・採用判断が未確定。担当と次の調査を記す |
| 要対応 | 採用する要求の実装、または検証が未完了。担当・残条件・次の作業を記す |
| 対応済み | 変更に関係する受入条件、満たす実現箇所、実行したPASS検証がすべてある |
| 影響なし | 新実装に該当する契約変更がない理由とソース・調査根拠、判断者・日付がある |
| 見送り | 要求を採用しない仕様判断の理由・根拠・承認者・日付がある |

「既存実装が既に満たす」は受入検証を経て「対応済み」にする。「影響なし」へ置かない。
「間に合わない」「sync成功」「テスト未実行」は、見送りや対応済みの根拠にならない。
意図的差異は `intentionalDifference: true` と `decision`（`reason` / `evidence` / `approvedBy` / `approvedAt`）を持つ。
承認記録には関係する仕様・Issue・ユーザーの判断履歴をリンクする。AI自身の都合を承認扱いにしない。
既存のPG通知保存などの承認済み差異も、触れる本家変更で再評価し、維持・変更の履歴を残す。

受入条件は入力・出力・エラー・保存・副作用・通常retryのうち変更に関係するものを具体化する。
検証は契約に合わせる。文字列・blobの一致は複製の受入条件には使えるが、DB適用・API動作や起動成功を示さない。
未実装と、実装があって検証待ちの状態はともに要対応とし、`next` に違いを記す。

## 抽出と持越しの手順

1. 前回記録の全「未評価」「要対応」を `carryIn` にID・状態・元の記録URL/パス付きで転記する。初回だけ空配列とその理由を記す。全体の未移植範囲は [BACKLOG](../BACKLOG.md) / #114へ接続する。
2. 本家旧新SHAの祖先関係とGitオブジェクトを確認する。履歴不足なら元リポジトリから必要な履歴を取得し、抽出できない状態は合格にしない。
3. リポジトリ全体をpath filterなしで列挙する。履歴の各コミットは第一親との差分を記録し、マージで導入・解消された変更も読む。`git diff --no-renames --name-only -z` を使い、削除・renameの旧新pathも落とさない。
4. 最終差分と途中履歴をそれぞれ読む。backend以外の設定、依存/lockfile、型/生成物、CI、コンテナ、テスト、フロント変更も影響を判断する。機械一覧から契約行へ双方向に追跡し、抽出漏れレビューを記録する。
5. 持越し行は同じIDと `carriedFrom` で必ず残す。完了や承認済み判断へ変更した場合も、その受入結果・判断履歴を残す。次の取り込みで未解決行が消えていないか、前回台帳と `carryIn` を別途照合する。
6. 抽出レビューとは別に各契約を検証して状態を更新し、対象新SHAと全持越しを含めて差分判定を保存する。

機械検査はpathとコミットの取りこぼし、ID対応、必須証跡、入力された持越しの消失を検出する。
1 path内の契約の分割漏れ、証跡の意味・真正性、`carryIn` 自体への転記漏れはレビューで確認する。
「全テスト成功」を抽出網羅性の証明にはしない。path対応だけで契約抽出レビューを省略しない。

## 取り込みの頻度・単位・見送り条件

この手順の運用基準は次のとおり。自動スケジュールや自動SHA更新は設定しない。

- 候補調査は週1回、および本家の正式リリース時・対象版のリリース判定前に行う。調査日・候補SHA・採用/延期理由を残す。移植が継続中でも候補調査と台帳追記は進められる。
- 取り込みは旧固定元から新候補までの連続した祖先範囲を1 batchにする。基本は本家のリリース単位。大きすぎる場合は依存する修正を分断しない連続範囲で分割し、各終点を固定する。
- 固定元を変える実作業は #136 の専用作業として、並行担当へ停止・基準切替を伝えて単独で行う。旧backendへの取り込みとbackend-upstreamの機械同期、新実装への業務移植を記録上も分ける。
- 取り込みの延期は未解決依存、検証環境不足、移植中の範囲との衝突など具体理由と再評価条件を記す。要求を捨てたことにはせず、元IDを持ち越す。
- 要求自体の見送りは、GOALSの初期範囲に照らした個別の承認済み仕様差だけに限る。fork固有機能は初期範囲外。UI内部だけなど新backendへ影響しない変更は、読解根拠を付けて影響なしとする。

## 判定と再現コマンド

試行する本家範囲は `d43954b333045e6c5fbd7e1b47592088980d5912..8e07cf085adf7009583d234a208e30436f020e26`。
既存の固定元は後者のまま。この作業で本家SHAや複製物を更新していない。

repo rootで実行する（Node.jsのみ。Gitオブジェクトが必要）。

```sh
node --test docs/backend-next/upstream-ledger/check.test.mjs
node docs/backend-next/upstream-ledger/check.mjs
node docs/backend-next/upstream-ledger/check.mjs --release
```

標準実行は記録形式とGit照合が妥当ならexit 0。`--release` は未評価・要対応が残ればexit 2、記録不備・Git照合不能はexit 1。
この例では `record: PASS` / `delta: BLOCKED`、未解決は `UL-002` / `UL-003` / `BASE-138` となる。
`BASE-138` は既存Issueを入力にした持越し試行であり、過去の本番差分台帳があったことは主張しない。

新batchでは3ファイルをコピーして更新し、checkerのJSON読込先をそのbatchへ向けて使う。過去の例を上書きしない。
checkerはこの試行のための局所検証であり、CIや製品のreleaseコマンドへ組み込んでいない。
全行を解決できても `DELTA_PASS` は対象差分の判定だけを示す。
製品リリースには全体の未移植・未検証一覧と承認済み差異、#114の全初期機能、配布物 #138、完全停止切替 #139の検証・承認が必要。
`productReleaseApproved` はこの検査では常にfalseであり、台帳形式の完成で製品全体を公開可としない。
