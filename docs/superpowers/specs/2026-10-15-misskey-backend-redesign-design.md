# Misskeyバックエンド再設計の基本方針

日付: 2026-10-15

更新: 2026-10-16（本家追従と保守、業務状態・副作用・回復・派生データ・観測・負荷制御の基本方針を詳細化）

状態: 会話で合意した設計原則をまとめた、文書レビュー用の設計書。実装計画は含まない。第16節では、合意した方針と、詳細化のための提案・未決事項を区別する。

## 1. 目的と対象範囲

Misskeyのバックエンドをforkとして再実装する場合の、責務・依存方向・データ整合性・外部互換性の原則を定める。

このリポジトリの目的を、実験的機能の早期提供から、バックエンドをリニューアルしたMisskeyの開発・保守へ変更する。既存のfork固有機能・変更はすべて引き継がず、新バックエンドへの移植対象・互換性維持の対象から外す。将来必要になった機能は、新バックエンドを基盤として改めて設計・実装する。

主な目的は、業務上の判断を通信、永続化、キャッシュ、非同期実行の都合から切り離し、変更範囲を把握しやすく、個別に検証できる構造にすること。フレームワークの置換だけでは目的を達成したとは扱わない。

基本構成は、機能ごとに境界を持つモジュラーモノリスとする。基盤にはHono、InversifyJS、TypeORM、BullMQを採用する。業務コードにはこれらの型や実行コンテキストを持ち込まない。

この文書はシステム全体の設計原則を対象とする。全機能の詳細仕様、最終的なモジュール分割、インターフェースの完全な定義、運用パラメーター、切り替え手順は対象外とし、個別の設計で定める。

## 2. 再実装と互換性

既存コード内で段階的にServiceを置き換えることは前提にしない。外部契約と既存データを引き継ぐ、別のバックエンド実装として設計する。

互換性の基準は、対象の本家コミットの仕様・挙動とする。第1節の方針に従い、既存fork固有のAPI・挙動は互換性維持の対象に含めない。

開発中は、投稿作成から取得・配信までのような一連の処理を新実装の中で通し、設計を検証する。本番の切り替えは旧バックエンドを完全停止して行う。無停止での切り替えや、旧新バックエンドの本番同時稼働は要件にしない。

互換性の対象は次の通り。

- REST APIの入力、出力、認証・認可、エラー、既定値、ページングと、成功時に保証する結果。
- 既存クライアントが使用するストリーミングの契約。
- ActivityPubによる外部サーバーとの通信。
- 本家の既存テーブルの構造とデータの意味。本家のマイグレーション履歴。

互換性はJSONの構造一致だけでは判定しない。永続化結果や処理のタイミングも、外部から観測される契約に含める。旧実装の不具合が疑われる差異は、互換維持か修正かを個別に判断する。

本家の業務データ構造の再設計は初期方針に含めない。具体的な制約が判明した場合に、その箇所の変更を再検討する。

## 3. 責務の分類

| 種類 | 責務 | 例 |
| --- | --- | --- |
| UseCase | 一つの業務操作を調整し、認可・トランザクション・副作用の境界を決める | 投稿作成、ロール付与 |
| 業務上の共通Service | 限定された業務能力を提供する | 実効ポリシー取得 |
| 純粋関数・Policy | 与えられた情報から判断・計算・変換する | ロール条件評価、公開範囲の判定 |
| 参照処理 | 必要な情報をまとめて取得し、参照目的に合うデータを返す | タイムライン取得 |
| 業務側のインターフェース | 呼び出し元が必要とする能力と契約を定める | RoleRepository、JobDispatcher |
| アダプタ | 通信や保存などの実装と、業務側の契約を接続する | Hono、TypeORM、Redis、BullMQを使う実装 |

更新と参照は責務を分けるが、別のデータベースを必須とはしない。一覧取得を多数のエンティティ別Repository呼び出しで組み立てることも強制しない。参照処理の実装は、必要なSQLなどを用いてまとめて取得できる。

`XXXEntityService`は残さず、その中の取得、業務判断、レスポンス変換を上記の責務へ分ける。単なるクラス名の変更では完了としない。

## 4. UseCaseと共通Serviceの依存規則

1. UseCaseは別のUseCaseを呼ばない。共通Service、DIコンテナ、コールバックなどを経由した間接呼び出しも禁止する。
2. 共通ServiceはUseCaseに依存しない。処理全体の成立と失敗の境界はUseCaseが所有する。
3. Service間の依存は許すが、循環は禁止する。インターフェース化や遅延解決だけで循環を隠してはならない。
4. モジュールをまたぐ依存は、所有モジュールが公開した狭いインターフェースを通す。公開契約を介した実際の依存も、循環の検査対象にする。
5. 共通Serviceは独自にトランザクションを開始・確定しない。共通の更新操作は、呼び出し元が所有するトランザクションに参加する。
6. 読み取りに見える操作が通知やジョブ投入を行うなど、契約から分からない副作用を持たせない。
7. 利用範囲が広いことを理由に、業務機能を汎用のCommonServiceへ集めない。実効ポリシー取得ならロール・権限を扱う領域が所有する。

複数のUseCaseでロール付与が必要な場合は、割り当て操作とその不変条件を共有できる。ロール付与UseCaseの認可・監査・通知まで一式を呼び回すことはしない。共有操作の契約と各UseCaseの責任を明示する。

イベントを受けて別のUseCaseを起動することは許す。ただし、独立して失敗・再試行できる後続処理に限る。同期で成立させるべき処理をイベントへ迂回させ、UseCase間呼び出し禁止の抜け道にしない。

### 4.1 業務状態の更新責任

業務上の状態と不変条件ごとに所有モジュールを決め、その更新経路を集約する。例えば、ロール割り当て・解除と、それに伴う制約の維持はロールモジュールが所有する。各UseCaseが必要なテーブルを自由に更新する構成にはしない。

所有の単位をテーブルと一律に一致させない。本家のDB構造を引き継ぐため、一つのテーブルに複数の業務領域の情報が存在し得る。ユーザー情報と投稿数のように同じテーブルへ保存される情報でも、業務上の責任を別々に検討する。

1. 同じ業務状態を変更する処理は、所有モジュールに集約する。
2. 他モジュールは、所有モジュールが公開する更新操作を利用する。所有モジュールのRepositoryを直接利用して更新せず、別のUseCaseを呼ぶ形にもしない。
3. 同時確定が必要な更新は、呼び出し元UseCaseが所有するトランザクションに参加する。公開された更新操作は独自にcommitしない。
4. 同じテーブルを複数モジュールが扱う場合は、それぞれの更新範囲を明示する。行全体の保存などにより、所有範囲外の値を上書きしない。
5. 複数領域にまたがる不変条件は、調整責任を持つUseCaseを明示し、各領域が維持する条件と区別する。
6. 参照処理は、必要な複数テーブルをまとめて取得できる。更新の所有権を理由に、テーブルごとの取得の繰り返しを強制しない。モジュール間の公開契約を通す依存規則は維持する。

具体的な所有範囲と公開する更新操作は、各機能の詳細設計で明記する。

## 5. 純粋関数とレスポンス構築

業務上の判断・計算・変換は、可能な範囲で純粋関数にする。現在時刻、乱数、設定値、閲覧者の条件など、結果に影響する外部情報は引数として渡す。

レスポンス変換はデータを取得しない。取得済みの情報と閲覧者の条件を受け取り、出力を構築する。Noteの変換からUserの取得を呼び、Userの変換からNoteの取得を呼ぶ構造は作らない。

可視性などのルールは独立したPolicyとして共有する。取得計画と必要な情報の収集は、UseCaseや参照処理が担当する。複数の対象を返す場合は、まとめて取得する責任もこの層が持つ。

## 6. フレームワークとアダプタ

| 基盤 | 担当する場所 |
| --- | --- |
| Hono | HTTP受付、認証情報の解釈、入力検証、UseCase呼び出し、既存API形式への変換 |
| InversifyJS | 起動時の依存関係の組み立てとインスタンスの寿命管理 |
| TypeORM | Repository・参照処理・トランザクションの実装 |
| BullMQ | ジョブの保存・実行・再試行を担う基盤実装 |
| Redis | キャッシュ、タイムライン、レート制限、配信など、それぞれのアダプタ実装 |

アダプタはライブラリ単位の万能ラッパーにしない。Redisを使う機能でも、キャッシュとタイムラインとライブ配信では別の契約を持つ。

インターフェースは業務側の必要な能力を表す。ライブラリの全APIを写した独自QueryBuilderや、Redisコマンドをそのまま公開する万能インターフェースは作らない。

業務コードにはHonoのContext、BullMQのJob、TypeORMのEntityManagerやEntityなどを渡さない。APIレスポンスのPacked型も、内部の業務モデルとして使用しない。業務上必要なデータ構造を定義するが、全Entityのコピーを機械的に作ることはしない。

DIコンテナを取り出すための業務向けインターフェースは作らない。業務コードはコンストラクタで依存を受け取り、組み立て部分以外からコンテナを参照しない。

認証された実行者の情報は、HTTP固有の型から変換して渡す。操作の業務上の認可はUseCase側に残す。ワーカーなどからの実行も実行者・実行権限を明示し、自動的な認可免除を設けない。

### 6.1 初期の実行プロセス構成

通常の起動では、Supervisor（監督プロセス）を親とし、その子としてHTTPサーバープロセスを1つ、ジョブワーカープロセスを1つ以上起動する。Supervisor自身はHTTP受付やジョブの業務処理を実行しない。

| プロセス | 責務 |
| --- | --- |
| Supervisor | 子の起動、起動完了の確認、終了監視、全体への終了指示 |
| HTTPサーバー | HTTP受付とリクエスト処理 |
| ジョブワーカー | キューからの仕事の取得と実行 |

DB・Redis接続やDIコンテナは、各子プロセスが必要なものを作る。親が作成した接続やServiceを、子プロセスと共有する設計にはしない。

HTTPサーバーとジョブワーカーを単独で起動できる入口も用意する。通常の起動ではSupervisorがそれらを起動し、将来、外部のプロセス管理基盤で別々に管理する場合にも利用できるようにする。

初期方針では、子の異常終了時は残りの子にも停止を指示し、全体を異常終了させる。Supervisorによる子だけの自動再起動は導入しない。起動・終了は第6.3節に従う。

### 6.2 設定ファイルと設定の受け渡し

本家の設定ファイル形式を維持し、既存の設定ファイルを利用できるようにする。DB、Redis、公開URLなど、本家と同じ用途の設定は名前と意味を引き継ぐ。新バックエンド固有の設定は専用の設定領域へまとめ、その具体的な名前と項目は詳細設計で決める。

設定の読み込み・検証は新バックエンド側で実装する。旧バックエンドの設定ローダーを直接利用せず、旧バックエンドのビルドを設定読み込みの前提にしない。

各モジュールには、設定全体ではなく、そのモジュールが必要とする項目だけを渡す。例えば、Roleのキャッシュに保持期限が必要なら、その値を渡し、DB接続情報などを含む設定全体へ依存させない。設定の読み込み・検証と、各依存へ必要な値を渡す処理は、起動時の組み立て部分が担う。

### 6.3 起動・終了の条件

| 場面 | 動作 |
| --- | --- |
| 起動時 | 設定、必要なマイグレーションの適用状況、DB・Redis接続、必要な初期化を確認してから、HTTP受付やジョブ取得を開始する |
| 起動失敗 | 初期化済みの接続などを閉じ、エラーで終了する |
| 終了要求 | 新しいHTTPリクエスト・ジョブの受け付けを止め、実行中の処理を待つ |
| 待機期限の到達 | 無期限には待たず、処理が残っていても終了する |

終了時の待機期限は設定可能とし、具体的な秒数は詳細設計で決める。実行中の処理を待った後、接続などのリソースを解放する。

中断されたジョブは、第10節の再試行・重複対策の契約で扱う。プロセスが終了したことだけを根拠に、実行中の更新がすべてrollbackされたとは扱わない。commitの結果が不明な場合は、第13節に従って結果不明として扱う。

### 6.4 定期処理の登録と実行

定期ジョブのスケジュールは、Supervisorの起動処理で登録する。HTTPサーバーや各ジョブワーカーが個別のタイマーで同じ業務処理を起動する構成にはしない。登録に必要な接続はSupervisor側で管理し、子との接続共有は行わない。

スケジュールには固定の識別子を付け、再起動・再登録で別のスケジュールとして増殖しないようにする。実際の業務処理はキューを通じてジョブワーカーが実行する。スケジュール登録の重複対策と、ジョブ自体の重複実行・前回分との重なりは分け、後者は各処理の契約で扱う。

初期構成では専用のスケジューラープロセスを設けない。Role系処理の初期実装では定期処理基盤を先に作り込まず、定期処理が必要になった段階で実装する。

### 6.5 HTTP接続と業務処理の境界

クライアントの生存状態や画面の状態を、業務処理の成立条件・取消条件にしない。HTTPとして受け付けたリクエストは、通常の入力検証・認証などを経て処理し、その結果をレスポンスへ変換して送信する。

HTTPアダプタが接続切断や送信エラーを観測する場合も、それをクライアントの終了や業務上の取消と同一視しない。接続状態を理由とするUseCaseの自動キャンセルは、更新・読み取りとも初期方針に含めない。

業務処理の成立とレスポンス送信の成否は区別し、送信できなかったことだけを理由に、確定済みの更新を取り消したり再実行したりしない。サーバー側の処理期限、プロセス終了、予約投稿の取消などの明示的な業務操作は、それぞれの契約に従う。

### 6.6 採用基盤とパッケージ構成

新バックエンドは`packages/backend-next`へ配置し、パッケージ名を`backend-next`とする。Supervisor、HTTPサーバー、ジョブワーカーはこの一つのパッケージへ置き、プロセスごとにパッケージを分けない。

本家由来のEntity・補助定義・マイグレーションは、専用ライブラリ`packages/backend-upstream`（パッケージ名`backend-upstream`）へ複製する。`backend-next`はこれをworkspace依存として利用し、パッケージをまたぐソースの直接参照は行わない。複製と公開APIは第16.2節に従う。

| 用途 | 採用する基盤 |
| --- | --- |
| 実行環境 | Node.js、TypeScript、ESM |
| HTTP | HonoとNode.jsアダプタ |
| DI | InversifyJS。起動時の組み立てに限定し、業務クラスは通常のコンストラクタで依存を受け取る |
| DB | TypeORMとPostgreSQL |
| Redis接続 | ioredis |
| ジョブ | BullMQ。業務ジョブの実装は必要になってから追加する |
| 検証 | Vitest、ESLint、TypeScriptの型検査 |

Node.js・TypeScriptと、TypeORM・BullMQ・ioredisなどの依存は、本家とのバージョン整合を優先する。具体的なバージョンは導入時に確認する。

`backend-next`の初期ビルドは`tsc`で`built/`へESMのJavaScriptを出力し、Node.jsで実行する。設定はNode.jsでの実行に合わせる。`backend-upstream`はJavaScriptと型定義を提供し、そのビルドを先に行う。旧バックエンドのビルドや成果物は前提にしない。

| コマンド | 役割 |
| --- | --- |
| `build` | 新パッケージのビルド |
| `start` | Supervisorから全体を起動 |
| `start:http`、`start:worker` | HTTPサーバー・ジョブワーカーを単独起動 |
| `migrate` | 第8.1節に従い二系統のマイグレーションを順に適用 |
| `typecheck`、`lint`、`test` | 型検査、lint、テスト |

`pnpm --filter backend-next start`など、ワークスペースのパッケージを指定して実行する。ビルドの入口とCIでは、依存する`backend-upstream`を先にビルドし、同じパッケージのコマンドを利用する。

## 7. トランザクション

UseCaseが、同時に確定させるべき更新の範囲を決める。トランザクションの開始・commit・rollbackの実装は基盤側が担う。

UseCaseにはEntityManagerを公開せず、そのトランザクションに結び付いたRepository群などを利用できる契約を提供する。同じ操作に参加する業務データと後続処理の依頼記録は、同一接続・同一トランザクションを使う。

トランザクション内の処理は、失敗を例外で伝える。基盤側はコールバックの正常終了後にcommitし、例外で終了した場合はrollbackして失敗を外へ伝える。失敗の戻り値を基盤側で例外へ変換する方式は採らない。commitの結果が不明な場合は、第13節の結果不明時の契約に従う。

参照する情報ごとに必要な鮮度と、今回の更新との関係を判断する。許容する古さの範囲にあり、今回の更新に影響されない情報は、トランザクション内でもキャッシュや操作内メモを利用できる。

判断に必要な時点のDB状態を要求する場合、取得対象と更新対象が同じ場合、参照・評価に依存する情報を同じ処理で変更する場合は、そのトランザクションの状態に基づいて取得・再評価する。キャッシュによって自分の更新や必要なロックを迂回しない。未commitの値を共有キャッシュへ書き込まず、その値に依存するメモもトランザクション外へ持ち出さない。

外部サーバーへの通信など、長く待つI/OをDBトランザクションへ含めない。入力検証時と更新時の間で競合し得る条件は、必要なロック・制約・再確認を個別の操作で設計する。

## 8. 本家とforkのデータ構造の所有権

同一PostgreSQLデータベース内に、fork専用スキーマを設ける。仮称を`backend_internal`とする。

| 対象 | 本家側 | fork側 |
| --- | --- | --- |
| 保存先 | 既存スキーマを維持 | 専用スキーマ |
| テーブル | ユーザー、投稿、ロールなど | 後続処理の依頼記録、処理済みイベント記録など、必要な内部基盤データ |
| マイグレーション | 本家のファイルと履歴を維持・追従 | 別ディレクトリ、別履歴テーブル、別実行設定 |
| 変更権限の範囲 | fork固有のDDLを加えない | forkが所有・管理する |

本家テーブルにfork専用のカラム、処理フラグ、トリガーを追加しない。fork固有の永続状態は専用スキーマで所有する。

マイグレーションの生成・適用・差分検査も二系統に分ける。fork側の生成・適用結果が本家側の構造を変更しないことを検証する。本家側へforkのマイグレーション履歴を混在させない。

実行時は両スキーマを扱えるDataSourceを用い、必要な更新を同じトランザクションで実行する。マイグレーションの分離を、実行時の接続やトランザクションの分離に持ち込まない。

本家のテーブル定義は永続化の互換対象とし、内部の業務モデルを同じ形へ固定しない。Repository実装が両者を対応付ける。本家の更新を取り込む際は、対応するスキーマバージョンとRepositoryの互換性を検証する。

本家のEntity定義・マイグレーションは、第16.2節の同期スクリプトで`backend-upstream`へ物理的に複製し、`backend-next`からパッケージ依存経由で利用する。本家由来の複製とfork専用の定義を分離し、複製したことを理由に本家側のスキーマや履歴の所有権を変更しない。

Redisなどにある既存状態も、切り替え前の棚卸し対象にする。再生成可能なキャッシュ、引き継ぐ必要がある状態、処理待ちの仕事を区別する。DB互換性だけで引き継ぎが完了したとは扱わない。

これらの引き継ぎは、第2節の完全停止を前提として設計する。旧新バックエンドが同じ状態を並行して更新できる互換性は要件にしない。

### 8.1 マイグレーションの実行責任と起動条件

サービスを完全停止した状態で、専用コマンドから本家由来、新バックエンド専用の順にマイグレーションを適用する。ディレクトリ・履歴・実行設定は二系統で維持し、実行を指示する入口を一つにする。

本家由来のマイグレーションは、`backend-upstream/migrations`が公開するクラスの一覧を利用する。`backend-next`側の専用コマンドがDB接続・履歴・実行設定を組み立てて適用する。パッケージをまたぐ相対パスや、ライブラリ内部のディレクトリを指すglobには依存しない。

両系統の適用に成功してから、HTTPサーバーとワーカーを起動する。適用途中で失敗した場合は、サービスを停止したまま対処する。

各HTTP・ワーカープロセスは、起動時に必要なマイグレーションの適用状況を確認し、未適用ならエラーで終了する。これらのプロセスからマイグレーションを自動適用しない。ワーカー数を増やしても、それぞれが適用処理を走らせる構成にはしない。

## 9. キャッシュ付きRepositoryと派生データ

キャッシュ付きRepositoryは全エンティティに一律実装しない。Roleなど、主要で頻繁に参照され、変更を速やかに反映したいデータに絞って採用する。RedisKVCacheはアダプタ内部の実装候補とする。

Roleの初期実装では、値はプロセス内メモリに保持し、Redisは無効化通知に使う。対象と変更反映の具体的な契約は、[Role詳細設計の第6.2節](2026-10-16-role-policy-update-design.md#62-材料のキャッシュと変更反映の契約)に従う。

Redisは必須基盤とする。必要なRedis操作が失敗した場合は処理のエラーとし、DBへのフォールバックで継続する縮退運転は設けない。通常のキャッシュミスによるDBからの取得は、Redis障害時のフォールバックとは区別する。commit後のキャッシュ無効化通知の失敗は、以下の方針に従い、確定済みの更新の成否とは分けて扱う。

整合性の契約は「通常は変更イベントで速やかに反映し、通知を取り逃しても有効期限などによって回復する」とする。更新成功後の全プロセスの読み取りに対する、即時の最新性は保証しない。

更新UseCaseは業務データの保存と必要な変更通知を調整し、キャッシュキーや削除処理には依存しない。キャッシュ側が通知を購読して無効化する。初期の基本方針は、値の直接差し替えより無効化・再取得とする。

キャッシュ無効化のためだけの通知は、更新のcommit後に送信を試み、後続処理の依頼記録には保存しない。通知を取り逃した場合は有限の有効期限などで回復し、通知の失敗だけを理由に確定済みの更新を失敗と扱わない。通知から別の業務上必要な仕事を起動する場合は、その用途の配送保証を別に設計する。

イベントとは別に、有限の有効期限による回復経路を持つ。Redisからメモリへ移すときに期限を更新し続けず、元データを再確認するまでの期限を引き継ぐ。更新前に開始した読み取りが無効化後に古い値を再投入する競合も、許容する古さの設計と検証に含める。

通知の欠落・重複・順序の逆転と、購読接続の再確立時の扱いを定める。イベントの到達だけをキャッシュの正しさの根拠にしない。

プロセスの再起動では、そのプロセスのメモリキャッシュは再作成される。ただし、他のプロセスやRedis上のキャッシュが同時に消えるとは仮定しない。通知を逃したキャッシュが残る場合も、元データを再確認するまでの期限で回復できるようにする。

更新直後のレスポンスは保存結果などから構築し、共有キャッシュから古い値を読み戻さない。

ロール定義・割り当て情報と、実効ポリシーの評価結果は別に扱う。割り当ての有効期限は評価の基準時刻に照らして確認する。条件付きロールが参照するユーザー属性なども、評価結果の変化要因になる。

ロールの実効ポリシーは、一つの業務操作内で取得・計算結果をメモ化して再利用する。複数リクエストにまたがる評価結果の共有キャッシュとは区別する。遅延処理は実行開始時刻、1リクエストで一息に行う処理は初回評価時刻を基準とする。再利用と再評価の境界は[ロール詳細設計の第6節](2026-10-16-role-policy-update-design.md#6-操作内のメモ化)に従う。

有効期限の秒数、キャッシュ対象、通知欠落後の再取得方針は各機能の詳細設計で決める。全キャッシュへ同じ期限を強制しない。Redis障害時は、上記の必須基盤としての扱いに従う。

### 9.1 派生データの正本と再構築

アプリケーションが管理する派生データごとに、元になる正本と、再構築できる範囲を明示する。例えば、Meilisearch側に登録する検索用データ、キャッシュされたタイムライン、集計値などを対象とする。

通常のSQLでカラムなどに張るPostgreSQLのindexと、PGroongaのindexは、DB側の管理・保守として区別する。アプリケーションが別途更新するMeilisearch側の検索用データと一括して扱わない。第10節の検索更新の例も、アプリケーションが管理する検索用データを意味する。

1. 派生データごとに、正本、再構築できる範囲、再構築の責任を持つ処理を明記する。
2. 再構築は専用の処理として用意し、投稿作成などの業務操作を再実行しない。再構築対象の更新に必要な処理を行い、対象外の通知や連合配送などを発生させない。
3. 再構築中に起こる更新・削除の扱いを決める。必要に応じてメンテナンス中の実行を選び、無停止での再構築を一律には求めない。
4. 再構築できない情報は、そのことを明示し、保存・復旧方針を別に決める。

例えば、DBの投稿を正本としてMeilisearch側の検索用データを作り直す場合、DBから投稿を読み出して検索用データを登録する。投稿作成UseCaseを再実行して通知や連合配送まで発生させる方法は採らない。

すべての情報を現在のDBから復元できるとは仮定しない。削除済み投稿を含む過去の統計などは、現在の投稿一覧だけから再現できない場合がある。復元できる履歴や期間も含めて設計し、第13.2節の保証範囲・上限と整合させる。

## 10. ジョブとイベントの契約

| 用途 | 契約 |
| --- | --- |
| ジョブ投入 | 指定した仕事をワーカーが実行する。再試行、期限、重複実行時の扱いを定義する |
| 業務イベント | 確定した事実を通知する。購読者ごとに必要な配送保証を定義する |
| ライブ配信 | 接続中のクライアントなどへ通知する。取り逃した場合の再取得方法を定義する |
| キャッシュ変更通知 | 変更を速やかに反映し、通知欠落から回復できるようにする |

全用途を、配送保証の分からない一つの汎用EventBusへまとめない。業務イベントを受ける独立した購読者には、それぞれの処理が届くようにする。複数ワーカーによる一つの仕事の分担と、複数購読者への通知を混同しない。

DB更新と一緒に確定すべき配送依頼やイベントは、同じDBトランザクションで「後続処理の依頼記録」として保存する。別の処理がその記録を読み、配信やジョブ投入へ接続する。必要な永続化と再送の契約をアダプタごとに定める。キャッシュ無効化のためだけの通知は、第9節の方針に従い、この記録を使わない。

この依頼記録を使っても、処理の重複や後続処理への反映遅延は発生し得る。受け手は操作の性質に応じて、重複実行に耐える設計にする。依頼記録だけで厳密な一回限りの実行や即時整合性を保証したとは扱わない。

### 10.1 非同期処理が参照する状態の時点

受付時の情報をすべて固定する方式と、実行時にすべて最新情報を取得する方式のどちらかへ一律に統一しない。確定した事実と、実行時に再確認する条件を分け、処理ごとに契約を定義する。情報を固定する時点が、予約の受理時なのか業務更新の確定時なのかも明示する。

1. 確定した出来事を、最新状態から別の出来事へ作り替えない。
2. 遅延して実行する操作は、実行時に再確認する権限・状態・取消条件を明示する。
3. 再確認で条件を満たさなかった場合は、取消・スキップ・失敗のどれとして扱うかを決める。
4. 実行直前の確認と実際の副作用の間にも競合はあり得るため、取消が有効になる境界を定める。既に送信したものは、送信前の取消と区別する。

次の表は個別設計で確認する観点を示す。各処理の具体的な条件と本家との互換動作を、この表だけで確定したとは扱わない。

| 処理 | 固定する情報 | 実行時に確認する条件 |
| --- | --- | --- |
| 予約投稿 | 投稿の指示内容、予約者、予約時刻 | 取消の有無、投稿可能な権限・アカウント状態 |
| 作成済み投稿の配送 | 配送する出来事の識別子と内容 | 削除・取消などにより配送を続けてよいか |
| 投稿削除の配送 | 削除した対象の識別情報 | 削除通知として必要な配送条件。投稿作成の権限とは別扱い |
| 検索インデックス更新 | 更新対象と、処理の古さを判別する情報 | 対象の現在の存在・状態 |

遅延処理の時間条件は、その実行試行の処理開始時刻を基準に評価する。登録日時や前回の試行の基準時刻は引き継がない。1リクエストで一息に行う処理では、最初に評価した時刻を基準に判断を揃える。長時間処理の段階や実行直前の再確認など、別の評価境界が必要な場合は、その境界で時刻と判断を更新する。

別の評価境界へ進んでも、以前の認可や状態確認が無条件に有効だとは仮定しない。一方、過去の投稿を取り消すための配送などに、現在の投稿作成権限を機械的に要求しない。処理の意味に沿って再確認する条件を選ぶ。

### 10.2 再実行と重複対策

重複による業務上の影響を防ぐ必要がある仕事は、処理の進み具合を永続状態から確認でき、再実行時に既に成立した結果を二重に作らないように設計する。同じ仕事のやり直しを識別できる情報を、再実行でも引き継ぐ。内容が同じでも、別に依頼された操作を同じ仕事とは扱わない。保証する障害の範囲と記録の保持期間は、第13.2節に従って定める。

例えば、メンション通知を作る仕事で、通知をDBへ保存した直後、ワーカーが完了を記録する前に停止する場合を考える。キュー上で完了が確認できず再実行されても、同じ通知を追加で作ってはならない。

通知依頼を「123番」として識別する場合、再実行でも123番を引き継ぐ。通知の保存と、その依頼による通知が成立したことを示す記録は、同じDBトランザクションで確定する。再実行では既存の結果を確認して終了でき、並行実行でも同じ依頼による通知は一つだけ成立するよう、一意制約などで保証する。既存の記録や制約で成立を判別できる場合は、別の処理済みテーブルを一律に追加する必要はない。

キュー上の実行中・完了状態だけでは、業務上の結果が成立したかを判断できるとは限らない。キューとDBの状態を別々に更新する間の停止も想定する。具体的な識別方法と進捗・結果の保存先は、各処理の詳細設計で決める。

外部への送信はDB内の記録と同時確定できるとは仮定しない。送信が成功していても応答を受け取れない場合を含め、結果不明時の回復と再送による重複の扱いを個別設計する。この節のDB内の通知作成例だけで、外部送信の厳密な一回限りの実行も保証したとは扱わない。

### 10.3 非同期処理の順序と古い仕事の扱い

順序によって結果が変わる処理は、順序を守る必要がある対象と範囲を明示する。対象ごとに順序を守るか、古い仕事の反映を防ぐかを、処理に応じて選ぶ。具体的な制御方法は個別設計で決める。

例えば、投稿作成時の検索登録と、直後の投稿削除に伴う検索削除を別々の仕事として実行する場合、検索削除の後に遅れて検索登録が完了すると、削除済みの投稿が検索結果へ復活し得る。これらは別の仕事なので、同じ仕事の重複実行だけを防いでも解決しない。この例では、同じ投稿についての検索更新を制御の単位として検討する。

検索など現在の状態を反映する処理では、古い仕事が削除や新しい更新を巻き戻さないことを検証する。投入・開始した順序だけでなく、再試行や並行実行によって反映が完了する順序も検証に含める。状態を確認してから反映する方式では、その間に起こる競合も扱う。

出来事そのものを伝える配送などは、第10.1節の契約と併せて必要な順序を定める。現在の状態へ合わせることを理由に、過去の出来事を別の意味へ作り替えない。

### 10.4 保存するジョブ・イベントの形式変更

保存するジョブ・イベントの形式を変更する際は、デプロイ前から残っている仕事の扱いを必ず決める。形式変更のための複雑な共通バージョン管理基盤を、一律に用意することは求めない。

- 旧形式の読み取り、保存済みデータの事前変換、旧形式の仕事の処理完了後の切り替えなどから、必要な方法を選ぶ。
- 互換性を維持する期間と対象を明示し、無期限の旧形式対応を前提にしない。
- 未対応の形式は推測で実行せず、確認できる失敗として扱う。

例えば、予約投稿を保存した後でその保存形式を変更する場合、新しいコードが以前の予約をどう処理するかを設計する。対応期間と残っている仕事の扱いは、第13.2節の上限・保証範囲とも整合させる。

fork内部に永続化するジョブ・イベントのペイロードは、形式を識別する`schemaVersion`を持つ。ジョブ・イベントの種類と`schemaVersion`の組で形式を識別し、種類ごとに番号を管理する。Misskey本体のリリース番号や、第10.3節の処理順序を判断する世代とは別の情報として扱う。

- 従来の解釈では正しく読めなくなる変更で番号を上げる。項目名や意味の変更などを対象とし、省略可能な項目の追加では互換性を確認して判断する。
- 受け取り側は、対応する番号であることと、その形式に沿った内容であることを検証する。番号だけで内容が正しいとは扱わない。
- 旧形式を直接読み取るか、変換するかは各処理で決める。番号の採用だけを理由に、汎用の変換機構を必須にしない。
- 新形式を読み取れるコードを先に用意してから、新形式の書き込みを始める。ロールバック時に旧コードが残った仕事を扱えるかも確認する。

## 11. キューの構成

ジョブの意味、実行ポリシー、物理キューの割り当てを分離する。

| 判断 | 内容 | 所有する側 |
| --- | --- | --- |
| 何をするか | Activity配送、予約投稿、エクスポートなど | 各機能 |
| どう実行するか | 再試行できる失敗、期限、重複時の扱い | 業務上の契約と実行ポリシー |
| どの資源で実行するか | キュー割り当て、ワーカー数、同時実行数 | 実行基盤・運用設定 |

UseCaseは型付けされた仕事の登録を依頼する。物理キュー名やBullMQのオプションを渡さない。業務上必要な実行時刻などは契約に含め、ライブラリ固有の設定へアダプタが変換する。

優先度や再試行の有無だけを理由に、物理キューを分けない。物理的な分離は、待ち時間の確保、負荷制御、障害の隔離を根拠に判断する。機能ベースの既存分割にもその理由があれば維持する。具体的なキュー一覧はこの文書では固定しない。

ワーカーはデータの検証・変換、実行コンテキストの準備、UseCase呼び出し、失敗の分類を担当する。業務判断を抱えず、UseCaseからBullMQの例外や再試行APIを呼ばない。

既存キュー管理APIの停止・再開・再試行なども互換性の対象とする。物理キューを統合する場合、旧キュー単位の制御を再現できる必要がある。旧名称だけを残し、停止によって無関係な仕事まで停止する構成にはしない。

### 11.1 処理能力を超える負荷の制御

仕事の到着量が処理能力を超える場合も想定し、再試行の上限だけでなく、新規の仕事と処理中・待機中の負荷を制御する。

1. 同時実行数、待機量、一度に処理する量に上限を設ける。値は処理ごとに決め、運用設定で調整できるようにする。
2. 大量配送や一括削除などは小さな単位に分けて進め、一つの仕事が処理枠を長時間占有しないようにする。
3. 特定の配送先の遅延や障害が、他の配送先・別機能の処理枠を使い尽くさないようにする。
4. 上限到達時の動作を決める。新規受付の制限、後続処理の遅延、欠落を許容した通知の省略など、処理の契約に応じて選ぶ。成功を返した業務に必要な仕事を、容量不足で黙って捨てない。

まず既存キューの並列数・投入量の制御と、必要な処理の分割で対応する。全機能に専用の制御基盤を用意することを前提にしない。具体的な方法と制限時のAPI動作は、第2節の互換性、第10節の契約、第13.2節の保証範囲と整合させる。

### 11.2 失敗が続く仕事の実行ポリシー（検討案）

失敗が続く仕事について、優先度を下げることと、再試行頻度を下げるために待ち時間を延ばすことを検討材料にする。採否と具体的な規則は、失敗理由、仕事の重要度、期限、対象ごとの順序を踏まえて決める。具体的な待ち時間や優先度の変更方法は、この文書では固定しない。

## 12. 投稿作成の代表フロー

1. HTTPアダプタが既存APIの入力を解釈し、実行者情報とともに投稿作成UseCaseへ渡す。
2. UseCaseが必要なデータを取得し、共通Serviceと純粋関数で権限、公開範囲、投稿条件などを判定する。
3. トランザクション内で競合し得る条件を必要に応じて再確認し、投稿、関連データ、必要な後続処理の依頼記録を保存する。
4. commit後、既存APIが要求する結果を返す。HTTPレスポンス形式への変換は外側で行う。
5. 後続処理の依頼記録から配送などの仕事を起動し、ワーカーが各UseCaseを実行する。

何を非同期化できるかは、旧APIの成功時に保証されていた挙動を確認して決める。副作用であることだけを理由に、すべてを後回しにしない。

## 13. エラーと成功の境界

UseCaseは成功時に結果を返し、失敗時は識別可能な例外を投げる。業務上の失敗もこの方式で表し、業務側で定義したエラーを使う。業務コードへHTTPステータス、本家のAPIエラー型、BullMQの例外などを持ち込まない。

HTTP・ワーカーの境界で例外を処理し、それぞれ本家互換のAPIエラーやジョブの失敗処理へ変換する。トランザクション内で操作の失敗を表す例外を握りつぶし、正常終了の値として返さない。エラーの種類は必要なものから定義する。

| 状況 | 扱い |
| --- | --- |
| 投稿条件違反、権限不足など | 業務エラーとして表現し、HTTP側が既存APIのエラーに変換する |
| commit前のDB障害 | rollbackし、操作失敗として扱う |
| commit結果が不明な通信障害など | 結果不明として扱い、安全性を確認せず自動再実行しない |
| commit後の配送失敗 | 投稿の成立を取り消さず、後続処理として再試行・記録する |
| ジョブの重複実行 | 操作ごとの重複対策で、二重の結果を生まないようにする |

ライブラリ固有の例外を業務層の公開契約にしない。失敗を一律に再試行可能とせず、一時的失敗、恒久的失敗、既に処理済みなどの意味をアダプタとの間で共有する。失敗の分類と、操作全体を安全に再実行できるかの判断は区別する。

### 13.1 部分完了からの回復と機能別の設計

DBとファイルストレージなど、複数の保存先・外部サービスをまたぐ操作は、途中まで成功した状態からの回復を設計する。第13.2節の前提条件と保証範囲のもとで、共通原則は次の通りとする。

1. 処理が途中で止まる場所と、各状態からの回復方法を明示する。
2. 回復に必要な識別情報と進捗は、プロセスが停止しても残るようにする。
3. 再開・後片付けの責任を持つ処理を定め、回復処理自体の失敗も、定めた上限の範囲で再試行できるようにする。

この基本方針を踏襲した、機能に特化する設計と実装を別途用意する。具体的な途中状態、再開する条件、取り消せる操作、後片付けの方法は、各機能が所有する。ファイル保存、アカウント削除、外部配送などに、同じ回復手順を一律に適用しない。

例えば、画像をストレージへ保存できた後でDBへのファイル情報登録に失敗すると、画像だけが残り得る。保存前に回復に必要な保存先などを記録しておく方式を候補とし、復旧時にはストレージとDBの状態を確認したうえで、登録の再開またはこの操作が作成した不要ファイルの清掃を判断する。実行中の処理や既に成立した登録と競合して、使用中のファイルを削除しないことも、この機能の詳細設計で扱う。

DBのrollbackが外部の操作も取り消すとは仮定しない。結果が不明な場合は、失敗したと決めつけて再実行や削除を行わず、第13節の結果不明時の扱いに従う。具体的な回復方式は、外部サービス側の保証も確認して選ぶ。

新たな永続状態が必要な場合は、第8節の所有権に従ってfork専用スキーマで管理する。機能別の回復設計でも、第4節の依存規則、第7節のトランザクション、第10節の非同期処理の契約を維持する。

### 13.2 保証の前提・範囲と自動回復の限界

想定する障害と前提条件を明示し、その範囲で必要な整合性と回復手段を提供する。無条件の完了保証は求めず、自動回復を打ち切れる設計にする。この原則は、重複対策、順序制御、部分完了からの回復と、回復処理自体にも適用する。

原理的に保証できないことと、費用・複雑さを考慮して保証しないことを区別する。例えば、相手が受信した後に応答だけが失われた場合、送信側だけでは結果を確定できない。相手側の重複排除や照会などの協力を前提にせず、必達と重複なしを同時に保証したとは扱わない。

| 対象 | 約束する範囲 |
| --- | --- |
| 投稿と必要な配送依頼の保存 | 同じDBトランザクションで確定させる |
| プロセス停止・一時的な障害 | 保存データが残り、処理を再開できる前提で回復可能にする |
| 外部サーバーへの配送 | 決めた期限・回数の範囲で試行する。相手側の処理完了までは保証しない |
| ストリーミング・キャッシュ通知 | 欠落を許容し、必要な状態は再取得できるようにする |
| 永続データの破損・全損 | バックアップなど、別の運用復旧設計で扱う |

1. 再試行の回数・期間、記録の保持期間、滞留量に上限を設ける。値と上限到達時の扱いは各処理の詳細設計で決める。
2. 再試行の上限に達したら自動処理を打ち切り、「失敗」「結果不明」などとして確認できる状態にする。記録自体も無期限保持を前提にしない。
3. 回復処理にも同じ上限の原則を適用する。回復を必ず成功させるための仕組みを際限なく追加しない。
4. 強い保証を追加する場合は、対象となる障害と、その保証に必要な費用・複雑さを明示する。

各APIが成功時に約束する結果は、第2節の互換性に従って維持する。後続処理の完了保証に上限を設けることを、APIの成立条件を無断で弱める理由にしない。

### 13.3 失敗・滞留の確認と観測データの保存

元の操作と後続の仕事を識別子で関連付けて調べられるようにする。失敗理由、最後の試行時刻、再試行中か打ち切り済みかを確認でき、滞留件数と待ち時間を把握できることを目指す。最初は構造化ログと既存のジョブ管理機能を利用し、必要な情報が不足する部分を補う。

観測用の履歴を業務用PostgreSQLへ蓄積する専用テーブルは追加しない。用途に応じて次の情報を利用する。具体的な出力先や収集基盤は個別設計で決める。

| 用途 | 利用する情報 |
| --- | --- |
| 元の操作と仕事の関連付け、個別の失敗調査 | 識別子を付けた構造化ログ |
| 現在のジョブ状態、失敗理由、試行情報、手動再実行 | 既存キューの管理情報 |
| 件数・待ち時間・失敗率などの傾向 | 集約したメトリクス |

ログ・キュー内の履歴・メトリクスも、保存先を変更しただけで無制限に増やしてよいとは扱わない。第13.2節に従って、保持期間、保持件数、容量などの上限を定める。個別の仕事の確認・再実行ができる範囲は、その記録が保持される期間・件数に限定する。失敗した仕事も、調査できることを理由に無期限保持しない。

手動で再実行する場合も、第10節の重複対策・状態確認を通す。ログへ記録する本文や個人情報は必要な範囲に絞る。

この節の対象は観測用の履歴であり、業務の成立や回復に必要な後続処理の依頼記録・重複対策・機能別の進捗記録は、第8節の所有権に従って別に設計する。それらも必要最小限の情報と保持範囲に絞り、観測用の長期履歴として兼用しない。キューの履歴を削除した後も重複対策が必要な場合は、観測用履歴の保持に依存せず、第10.2節の契約で扱う。

## 14. 検証方針

| 検証 | 対象 |
| --- | --- |
| 純粋関数の検証 | 境界値、時刻、有効期限、公開範囲、ロール条件と優先順位など |
| UseCaseの検証 | 認可、処理の調整、失敗時の判断。HTTPサーバーやDIコンテナを起動しない |
| アダプタの結合検証 | 実DB・Redis・BullMQで、インターフェースの契約を満たすこと |
| 障害・競合の検証 | rollback、commit後の中断、重複、順序逆転、通知欠落、キャッシュの再投入競合など |
| 保証範囲と上限の検証 | 明示した前提のもとでの回復、再試行の打ち切り、失敗・結果不明の記録、保持期間や滞留量の上限到達時の扱い |
| 派生データの再構築の検証 | 正本からの復元範囲、再構築中の更新・削除、対象外の通知や連合配送を発生させないこと |
| 互換性の検証 | 旧実装と新実装に同条件の入力を与え、外部から観測できる結果を比較する |
| マイグレーションの検証 | 二系統の履歴と適用範囲、本家側の構造をfork側が変更しないこと |
| 依存規則の検証 | 禁止import、公開型への基盤型の混入、UseCase間依存、モジュール・Service間の循環 |

旧実装との比較では、時刻や生成IDなどの非決定的な値を制御または意味を保って正規化する。旧実装との差分がないことだけでなく、合意した業務ルールへの適合も検証する。

### 14.1 最小基盤とRole初期実装の受け入れ条件

第15.2節の初期実装では、検証を次の四つに分ける。

| 検証 | 確認すること |
| --- | --- |
| 単体 | 条件付きロール、割り当ての失効、優先順位、資格判定、UseCaseの認可と処理順序 |
| DB・Redis結合 | 更新と監査の同時確定、rollback、並行更新、キャッシュ通知・期限・無効化 |
| HTTP | `admin/roles/show`・`admin/roles/update`の認証、入力・出力・エラーと、保存後のポリシー反映 |
| 起動・終了 | Supervisorからの起動、依存先の初期化失敗、正常終了、子の異常終了 |

単体検証ではHTTPサーバー・DIコンテナを起動しない。結合検証では実際のPostgreSQL・Redisを使う。HTTPからの更新後に、別の操作で評価した実効ポリシーへ変更が反映されることも検証する。具体的な業務上の条件はRole詳細設計の第4節に従う。

互換性の期待値は、第16.2.1節で固定した本家コミットの実行結果から確定する。初回と、本家追従によって対象の契約が変わったときに新旧を比較し、通常のCIでは記録した期待値を使う。監査保存失敗時のrollbackなど、合意した仕様差は別の期待値として明記する。

CIでは、初期範囲の新パッケージと専用ライブラリについて、次を必須とする。

- 同期元との一致確認、ビルド、型検査、lint。
- 上表の単体・結合・HTTP・起動終了の検証。
- マイグレーションの適用と、第16.2.2節で定めた対象範囲のスキーマ差分検査。

この範囲が通り、合意した仕様差を説明できることを、最初の実装の受け入れ条件とする。投稿・配送など未実装の機能の検証は、その機能を追加する際に広げる。

## 15. 個別設計へ分ける単位

全バックエンドを一つの実装計画にはしない。共通原則をこの文書で固定したうえで、次のような単位で仕様と実装計画を分ける。

- 実行コンテキスト、依存関係の組み立て、トランザクションの契約。
- fork専用スキーマ、独立マイグレーション、後続処理の依頼記録とジョブ・イベント基盤。
- Roleを題材にしたRepository、キャッシュ、Policy、UseCaseの一連の設計。
- 投稿作成・取得・配信を通す、複数モジュール間の設計。
- ファイル保存など、複数の保存先・外部サービスをまたぐ操作に特化した、途中状態・再開・後片付けの設計。
- Meilisearch側の検索用データ、キャッシュされたタイムライン、集計値などの正本・復元範囲・再構築の設計。
- 他機能の詳細設計と、API・ストリーミング・ActivityPubの互換性検証。
- 完全停止を前提とした、Redis上の状態と既存ジョブの引き継ぎ・運用の設計。
- 本家の取り込みと新バックエンドへの移植を支援するスキル、追従状況の記録、リリース判定の設計。

この一覧全体の実装順や作業項目は確定しない。最初の詳細設計対象は第15.1節のロールの一連の処理とする。各単位で担当範囲、公開契約、整合性、エラー、受け入れ条件を定めてから実装計画を作る。

### 15.1 最初の詳細設計対象

最初は、ロール定義の取得・更新を入口として、「ロールのポリシーを変更し、その変更がキャッシュを経て、ユーザーの権限判定へ反映されるまで」を詳細設計する。単にロールを取得・保存できることだけでは、モデルケースの検証完了とは扱わない。

選定理由は、他の機能が利用する権限・実効ポリシーの基盤であり、認可、永続化、純粋な条件・優先順位の評価、変更イベント、キャッシュ、監査の責務を具体的な処理で検討できるためである。既存の文書で例示されていたことだけを選定理由にはしない。

この一連の処理から、UseCase、業務上の共通Service、Policy、Repository、トランザクション、キャッシュの契約を具体化する。後続処理の依頼記録は、必要な用途について契約を定め、キャッシュ無効化のためだけには用いない。実効ポリシーの評価と、管理者・モデレーター資格の判定は、それぞれの業務上の意味と本家の挙動を確認して設計する。

ロールだけで全バックエンドの設計を検証したとは扱わない。その後、投稿作成・削除・配送で、複数領域の更新、大量ファンアウト、外部通信などの別の性質を検証する。ファイル保存などの部分成功と回復も、各機能の詳細設計で扱う。

ロール変更と、その管理操作の監査記録は、同じDBトランザクション内で同期的に保存し、一緒に確定させる。監査記録を保存できなければ変更もrollbackする。これは第13.3節の観測用履歴とは区別する。

個別の合意事項、本家の挙動、残る設計事項は、[ロールのポリシー更新と反映の詳細設計](2026-10-16-role-policy-update-design.md)へまとめる。

### 15.2 初期実装の進め方

最小限の基盤を先に用意し、その上に第15.1節のRole系処理を作る。基盤の範囲はRole系処理を実装・検証するために必要なものに絞り、他機能でしか使わない汎用基盤を先に作り込まない。

Role系処理を通す中で、基盤と公開契約の妥当性を確認し、必要な部分を具体化する。基盤とRoleの詳細設計・実装計画では、それぞれの最小範囲と受け入れ条件を定める。

#### 15.2.1 最小基盤の範囲と完成条件

最小基盤には、次を含める。

- 新パッケージのビルド、設定読み込み、DI。
- Supervisor、HTTPサーバー、ジョブワーカーの起動・終了。
- DB・Redis接続、マイグレーションの適用・適用状況の確認。
- トランザクション実行、ログ、テスト環境。

依存先を確認して起動でき、正常終了、起動失敗、子の異常終了を合意した方針で扱えることを、この段階の完成条件とする。ワーカーは起動・終了の枠まで用意し、業務ジョブは必要になった段階で追加する。

#### 15.2.2 最初のRole実装の範囲と完成条件

HTTP APIは`admin/roles/show`と`admin/roles/update`を対象とする。これらに必要な既存トークン認証、モデレーター・管理者資格の判定、ロール更新と監査の同時保存、キャッシュへの変更反映、実効ポリシー取得を実装する。実効ポリシーには、手動・条件付きロール、割り当ての失効、優先順位を反映する。

HTTPから更新し、DBと監査へ保存され、別の操作で評価した実効ポリシーへ変更が反映されることを完成条件とする。認可拒否、rollback、並行更新、通知欠落についても、合意済みの挙動を検証する。評価結果はテストで確認し、確認用の独自APIは追加しない。

ロールの作成・削除・付与・解除、ログインやトークン発行、管理画面は後続に回す。初期のユーザー・トークン・ロール・割り当てはテストデータとして用意する。詳細は[Role詳細設計の第1.1節](2026-10-16-role-policy-update-design.md#11-初期実装の範囲と完成条件)に従う。

### 15.3 この段階で整理する決め事

共通原則は第3〜14節を前提とし、直近では最小基盤とRole系処理の詳細設計・実装計画に必要な判断へ絞る。項目1〜6の方針は下表の参照先で合意済みとする。具体的な型・既存仕様の調査結果・検証ケースなどは、これらの方針に沿って詳細化する。

| 順序 | 決め事 | この段階で決める範囲 |
| --- | --- | --- |

- 終了待機時間、再試行間隔、並列数、キャッシュTTLなどの具体的な既定値は、利用箇所の実装・検証に合わせて決める。許容する古さや打ち切り時の意味など、挙動を左右する契約は各機能の詳細設計で先に定める。

## 16. 本家の取り込みと保守

### 16.1 合意した基本方針

- `packages/backend`にはリニューアルのための変更を加えず、そのまま残す。本家からの更新はこのパッケージにも取り込む。「変更しない」は、本家のある時点のコードへ固定する意味ではない。
- リニューアルしたバックエンドは、同じリポジトリ内の別パッケージ`packages/backend-next`として作成する。パッケージ構成とコマンドは第6.6節に従う。
- 本家をマージする際は、旧バックエンドの差分から対応すべき変更を抽出し、新バックエンドへ動作を移植する。この作業をLLMが支援するスキルを用意する。
- 本家の変更は、新機能も含めて原則追従する。見送る変更は個別に判断し、理由を記録する。未移植であることを、見送りの判断として扱わない。
- 既存のfork固有変更は引き継がず、移植支援スキルの対応対象にも含めない。必要になった独自機能は、新バックエンド上で改めて設計・実装する。
- 本家のEntity定義・マイグレーションなどは、専用ライブラリ`packages/backend-upstream`へ物理的に複製し、スクリプトで同期する。`backend-next`はこれをworkspace依存として利用する。機械的な同期と、新設計への動作の移植を分担する。

旧バックエンドは本家の挙動を確認する参照実装としても利用する。複製元と互換性比較元は、対象の本家コミットに対応するコードとし、既存forkの独自変更を混入させない。新バックエンドは、第3〜13節の責務・依存規則に沿って実装する。移植する対象は動作と契約であり、旧実装のクラス構成や依存関係を写すことではない。

第16.2節は合意した複製方針、第16.3節は合意した進捗管理の基本方針を示す。第16.4〜16.5節の詳細な作業・検証手順は提案であり、詳細設計で確認する。

### 16.2 パッケージの境界と物理ファイルの複製

新バックエンドから旧バックエンドのソース・ビルド成果物を直接importせず、旧バックエンドのビルドを新バックエンドのビルドの前提にしない。本家のEntity定義・マイグレーションと必要な補助定義を、専用ライブラリ`packages/backend-upstream`へ複製して利用する。共有パッケージへの切り出しのために旧バックエンドを変更する方式は採らない。

| 対象 | 扱い |
| --- | --- |
| 本家のEntity・必要な補助定義 | 本家と同じディレクトリ構造・内容で`backend-upstream/src/`へ複製し、複製先は直接編集しない |
| 本家のマイグレーション | 全履歴を`backend-upstream/migration/`へ複製する。内容・ファイル名・クラス名などの識別情報を維持し、既存の適用履歴を引き継ぐ |
| 新実装のRepository・業務モデル | 新設計に沿って実装し、複製したEntityとの変換は永続化アダプタが担当する |
| fork専用のEntity・マイグレーション | `backend-next`側で本家由来の複製と別管理し、第8節の専用スキーマと独立した履歴を使用する |

複製対象とその依存を明示する。`models/`にはNestJSのRepositoryModuleなども含まれ、Entityからディレクトリ外の定義への参照もあるため、ディレクトリ全体を無条件にコピーしない。マイグレーションが利用する外部ライブラリなど、実行に必要な依存も確認する。

複製したソースのimportや内容は変換しない。相対importは本家のディレクトリ構造を維持して解決する。`@/…`などの別名参照が必要になった場合は、ライブラリ側のビルド設定で解決する。`tsconfig.paths`だけでは出力JavaScriptのimportは変わらないため、必要な解決処理をビルドに用意する。DB定義や業務上の意味は変更しない。

ライブラリはJavaScriptと型定義を提供し、`backend-next`は通常のパッケージとして参照する。Entityは`backend-upstream/entities`、マイグレーションのクラス一覧は`backend-upstream/migrations`という別の公開入口にし、Entityの利用だけでマイグレーション一式を読み込まないようにする。公開入口は複製領域と分離し、マイグレーション一覧は同期スクリプトが自動生成する。マイグレーションの内容や識別情報は変更しない。

Entityを参照するのは永続化アダプタに限定し、業務モデルとして使わない。ライブラリはDB接続設定やマイグレーションの実行責任を持たず、必要な外部依存と実行可能な定義を提供する。

同期処理は次を満たす。

- 複製元の本家コミット、対象ファイル、複製先、公開入口の生成規則とビルド設定を記録する。
- 複製対象の追加・変更・削除を検出し、反映する。
- 同じ入力と生成規則から同じ出力を再現できるようにし、CIで同期漏れと複製先の手編集を検出する。
- 複製対象に新たな依存が加わった場合は検出して停止し、複製範囲やビルド設定を見直す。旧バックエンド全体へ依存範囲を自動拡大しない。

同期スクリプトがファイルの複製・削除・一致確認と公開入口の生成を担当し、LLMスキルは差分の意図の分析、新実装への動作の移植と検証を担当する。同期が成功したことだけでは、業務処理やRepositoryの対応完了とは扱わない。

パッケージを分けても、ワークスペース設定、lockfile、起動・ビルドスクリプト、CI、コンテナ設定などの共通ファイルでは本家との差分が残る。これらは追従時の確認対象とする。旧バックエンドを残すことと、本番で両バックエンドを同時稼働させることは分けて扱う。

#### 16.2.1 初期の参照基準と同期範囲

初期の本家コミットは`8e07cf085adf7009583d234a208e30436f020e26`（2026-10-14）に固定する。調査時点のHEADとローカルの`upstream/develop`が一致する地点であり、常に最新を使う指定ではない。以後の変更は、第16.3節の本家追従作業として明示的に進める。

複製元は作業中のファイルではなく、指定したコミットのGit上の内容とする。元コミット・同期対象などの記録は、`packages/backend-upstream/upstream-sync.json`へ保持する。

EntityはRole、RoleAssignment、User、Meta、ModerationLog、AccessToken、Appを入口として、必要な参照先のEntityと補助定義まで複製する。初期の依存にはDriveFile、DriveFolder、`models/util/id.ts`も含まれる。これらの定義の複製を、その機能全体の実装範囲へは広げない。NestJSのModuleや業務Serviceは対象に含めない。

本家のマイグレーションは基準コミットの全履歴を引き継ぐ。初期の業務機能がRoleに限られていても、DBをRole用の一部テーブルだけの構成にはしない。

#### 16.2.2 適用状況とスキーマの検査

第8.1節の起動時検査は、必要なマイグレーションが適用済みかを履歴で確認する。EntityとDB定義の差分検査とは区別する。

スキーマの差分検査は検証用DBで行う。本家側は同期したEntityに対応する範囲を確認し、まだEntityを取り込んでいない本家テーブルを削除対象として扱わない。新バックエンド専用側の検査も第8節の所有権に従い、本家側の構造を変更しないことを確認する。

### 16.3 取り込みと移植の進捗

「本家コードの取り込み済み」と「新バックエンドへの対応完了」を区別して記録する。本家をマージできたことだけで、追従が完了したとは扱わない。

差分抽出では、前回取り込んだ本家コミットと、今回取り込む本家コミットを固定する。fork側の変更を混ぜずに本家の更新範囲を特定し、その範囲の履歴と最終的な差分を併せて確認する。移植が未完了のまま次の取り込みを行っても、以前の未対応項目を残して追跡する。

本家を取り込んだ時点で変更一覧を残す。対応記録は、まずリポジトリ内のファイルで管理し、専用の管理システムは設けない。具体的な保存場所・形式は別途決める。

変更ごとに、元コミット、変更された契約、影響する新実装、対応状況、検証結果を記録する。状況は少なくとも「未評価」「要対応」「対応済み」「影響なし」「見送り」を区別する。「影響なし」「見送り」には根拠を残し、判断できない項目を対応済みにしない。

スキルは差分の分析と新実装への動作の移植を支援し、対応記録と検証結果を残す。コードを生成したことや、スキルを実行したことだけでは対応済みにしない。

本家コードの取り込み地点と、変更ごとの対応・検証の完了状況をそれぞれ追跡する。公開する版は、対応する本家コミットと既知の差異を説明できる状態にする。

#### 16.3.1 対応状況の判定基準

判定の単位は、本家の変更が要求する振る舞い・契約とする。1コミットに複数の変更があれば分け、複数コミットで一つの修正を構成する場合はまとめる。各項目から元コミット・差分をたどれるようにする。

「対応済み」は、次の三つが揃った状態とする。

1. 本家の変更前後から受け入れ条件を抽出し、入力、結果、副作用、失敗時の扱いなど、変更に関係する要求を明文化している。
2. 新バックエンドでその条件を実現する箇所を説明できる。移植したコードだけでなく、既に条件を満たしていた既存実装も対象とする。
3. 条件に適したテストや再現手順を実行し、条件を満たす検証結果を記録している。関係のない既存テストの成功だけを根拠にしない。

| 状況 | 判定基準 |
| --- | --- |
| 未評価 | 新バックエンドへの影響や採用要否をまだ判断できていない |
| 要対応 | 採用する要求に対して、実装または必要な検証が未完了である |
| 対応済み | 受け入れ条件、実現箇所、検証結果の三つが揃っている |
| 影響なし | 新バックエンドに該当する変更がないことを説明できる。本家の実装内部だけの整理などが該当する |
| 見送り | 要求を採用しないという意図的な仕様判断と、その理由が記録されている。移植が間に合わないことだけを理由にしない |

例えば、本家で「期限切れの管理者ロールでも管理操作ができる不具合」が修正された場合は、「期限切れなら操作を拒否し更新しない」「有効な管理者は引き続き操作できる」などを受け入れ条件にする。新実装が既に条件を満たしていれば、コード変更なしでも検証結果を根拠に対応済みとできる。この場合は影響なしに分類しない。

変更を一覧へ抽出できているかと、抽出した変更へ対応できているかは別に確認する。元の差分・履歴と対応記録を照合し、抽出漏れや未評価の変更を確認する。対応項目のテストが成功したことだけでは、抽出の網羅性の根拠にしない。

あらゆる挙動の完全一致の証明までは求めない。変更の影響範囲に応じて検証方法を選び、判定の根拠を残す。必要な条件を確認できていない場合は、対応済みにしない。

#### 16.3.2 取り込みとリリースの条件

- 以前の移植が未完了でも、次の本家の取り込みを進めてよい。未対応項目は引き継ぐ。
- リリース対象とする本家コミットを明示し、その範囲には「未評価」「要対応」を残さない。以前から持ち越した項目も判定対象に含める。
- 「見送り」は要求を採用しないという仕様判断がある場合に限る。未移植であることを、リリースのために見送りへ読み替えない。

### 16.4 移植支援スキルの責務（提案）

1. 対象の本家コミット範囲と、前回から持ち越した未対応項目を読み込む。
2. `packages/backend`の差分を入口に、関連するテスト、API型・生成物、設定、依存関係、マイグレーションなどの変更も調べる。バックエンド配下に差分がなくても影響する更新を確認対象に含める。
3. 変更を、機能追加、不具合修正、認証・認可、API・ストリーミング・ActivityPub、永続化、ジョブ、運用などの観点で分析する。旧実装内部だけのリファクタリングは、外部契約や不具合への影響を確認して移植要否を判断する。
4. 変更の意図と変更前後の動作を整理し、新実装のUseCase、Policy、参照処理、アダプタなどへ対応付ける。差分の周辺と呼び出し元・先も必要に応じて調べる。
5. 対応内容と受け入れ条件を示し、採用する変更を新実装の設計に沿って移植する。判断が必要な仕様差や解析できない変更は明示する。
6. 対応する検証を実行し、第16.3.1節の判定基準に沿って変更ごとの記録を更新する。コードの生成だけでは移植完了にしない。

スキルは本家差分と新実装の対応関係を説明できる成果物を残す。LLMの分析だけを網羅性の根拠にせず、対象ファイル・コミットの一覧と変更ごとの判定を突き合わせ、未評価の変更を検出できるようにする。スキルの実行自体は、マージ、公開、外部送信の許可を意味しない。

### 16.5 互換性と保守の検証（提案）

第14節の互換性検証を、移植した変更の受け入れ条件にも使用する。旧実装の既存テストは仕様を把握する資料として活用し、新旧実装に同じ契約を検証できるテストを整える。認可、エラー、保存結果、配信やジョブなど、レスポンス以外への影響も確認する。

比較する旧実装は、対象の本家コミットに対応する版を固定する。新旧の検証は分離したDB・Redis・ジョブ環境などで実行し、状態の干渉や外部への二重配送を避ける。本家の変更が既存の意図的な差異に触れた場合は、その差異を維持するかも再評価する。

### 16.6 次に決めること

- 原則追従に対して例外的に見送る条件。
- 取り込みの頻度・単位。
- 第6.6節のパッケージ構成・コマンドを、ワークスペース設定・CI・コンテナ設定などへ組み込む具体的な変更。
- 第16.2節に沿った同期スクリプト・ライブラリのビルドと、第8.1節のマイグレーション専用コマンド・検査を実装する具体的な手順。
- 対応記録の保存場所・形式と、移植支援スキルの入出力・検証手順。

## 17. 技術的根拠

本文の「後続処理の依頼記録」は、一般にTransactional Outboxと呼ばれる方式を用いる。ActivityPubのoutboxとの混同を避けるため、本文では別の呼び名を使う。

- [PostgreSQL: Schemas](https://www.postgresql.org/docs/current/ddl-schemas.html): 同一DB内の名前空間と、スキーマをまたいだアクセス。
- [TypeORM: Multiple data sources, databases, schemas and replication setup](https://typeorm.io/docs/data-source/multiple-data-sources/): 一つのDataSourceでの複数スキーマの利用。
- [TypeORM: Transactions](https://typeorm.io/docs/transactions/): トランザクションに属するEntityManager・接続の利用。
- [TypeORM: Migrations Setup](https://typeorm.io/docs/migrations/setup/): ファイルパスだけでなく、マイグレーションクラスを一覧で登録できること。
- [TypeScript: paths](https://www.typescriptlang.org/tsconfig/paths.html): 別名参照の型解決設定だけでは、出力JavaScriptのimportは変わらないこと。
- [Redis: Pub/Sub](https://redis.io/docs/latest/develop/pubsub/): 配送はat-most-onceであり、切断時などに失った通知は再送されない。
- [Node.js: HTTP ServerResponse](https://nodejs.org/api/http.html#class-httpserverresponse): HTTP接続の途中切断を観測し得ることと、レスポンス送信完了がクライアントの受信完了を保証しないこと。
- [Transactional outbox pattern](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html): DB更新とイベント記録の原子性、および重複への対処。
