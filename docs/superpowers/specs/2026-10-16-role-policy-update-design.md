# ロールのポリシー更新と反映の詳細設計

日付: 2026-10-16

状態: 初期実装の方針と検証範囲は合意済み。合意事項と調査時点の参照実装の挙動を記録する。残る具体化・調査事項は第5節で区別し、実装計画は含まない。

前提: [Misskeyバックエンド再設計の基本方針](2026-10-15-misskey-backend-redesign-design.md)。特に、業務状態の所有権、依存規則、トランザクション、キャッシュ、保証の範囲に従う。

## 1. 対象と目的

ロール定義の取得・更新を入口として、ロールのポリシー変更がキャッシュを経てユーザーの権限判定へ反映されるまでを設計する。ロールの取得・保存だけを実装して検証完了とはしない。

実装は、基本方針の第15.2節に従い、最小限の基盤を先に用意してから、その上にRole系処理を作る順序とする。

この流れを通じて、UseCase、業務上の共通Service、純粋なPolicy、Repository、トランザクション、変更イベント、キャッシュ、監査の責務を具体化する。条件付きロール・割り当ての期限・ポリシーの優先順位などについても、本家の挙動と依存を確認し、初期の検証で扱う範囲を明記する。

ロールの実効ポリシーと、管理者・モデレーター資格の判定は、それぞれの業務上の意味を確認する。ロール更新が関わることを理由に、両者を一つの判定へ置き換えない。

### 1.1 初期実装の範囲と完成条件

| 対象 | 初期範囲 |
| --- | --- |
| HTTP API | `admin/roles/show`、`admin/roles/update` |
| 認証・認可 | 対象APIに必要な既存トークン認証と、モデレーター・管理者資格の判定 |
| 更新 | 指定項目のロール更新と監査記録を、同じトランザクションで保存 |
| 変更反映 | キャッシュ無効化通知と、有効期限による回復 |
| ポリシー評価 | 手動・条件付きロール、割り当ての失効、優先順位を反映した実効ポリシー取得 |

HTTPから更新し、DBと監査へ保存され、別の操作で評価した実効ポリシーへ変更が反映されることを完成条件とする。認可拒否、rollback、並行更新、通知欠落について、第3〜4節の合意済みの挙動も検証する。評価結果の確認にはテストを使い、確認用の独自APIは追加しない。

ロールの作成・削除・付与・解除、ログインやトークン発行、管理画面は後続に回す。初期のユーザー・トークン・ロール・割り当てはテストデータで用意する。認証済みの実行者を固定するだけの検証で、HTTPからの既存トークン認証の検証を代替しない。

## 2. 現在の参照実装

参照先は調査時点の`packages/backend`。互換性を検証する際は、基本方針に従って比較対象の本家コミットを固定する。

- [admin/roles/show](../../../packages/backend/src/server/api/endpoints/admin/roles/show.ts)は、モデレーター権限を要求してロールを取得・変換する。
- [admin/roles/update](../../../packages/backend/src/server/api/endpoints/admin/roles/update.ts)は、管理者権限を要求し、取得したロールと変更内容・実行者をRoleServiceへ渡す。
- [RoleService](../../../packages/backend/src/core/RoleService.ts)の`update()`は、ロール更新と再取得の後に変更イベントを発行し、実行者があれば監査記録を依頼する。この呼び出しでは監査保存の完了を待たず、ロール更新と監査保存を同一トランザクションにもしていない。
- 同Serviceは変更イベントを受けてメモリ上のロールキャッシュを更新する。実効ポリシーの計算は、適用されるロール、優先順位、基本ポリシーなどを使う。
- [ModerationLogService](../../../packages/backend/src/core/ModerationLogService.ts)は、実行者・操作種別・操作内容を[moderation_log](../../../packages/backend/src/models/ModerationLog.ts)へ保存する。

## 3. 合意したロール変更の成立条件

ロール変更と、その管理操作の監査記録は、同じDB接続・同じトランザクション内で同期的に保存し、一緒に確定させる。監査保存を別ジョブへ分離しない。

| 状況 | 扱い |
| --- | --- |
| ロール変更と監査記録の保存が成功し、commitを確認できた | 保存処理が成立したとして扱う |
| ロール変更または監査記録の保存に失敗 | トランザクション全体をrollbackし、変更を成立させない |
| commitの結果が不明 | 基本方針の結果不明時の扱いに従い、安全性を確認せず自動再実行しない |

UseCaseが成立範囲を所有し、ロールと監査を保存する操作はそのトランザクションに参加する。監査側が別の接続で保存したり、独自にcommitしたりしない。業務コードにはEntityManagerなどの基盤型を公開しない。

この監査記録は管理操作そのものの履歴であり、ジョブの各試行を記録する観測用の履歴ではない。既存の本家テーブルと履歴の互換性を保ち、保存する内容と保持方針を詳細化する。

参照実装に対して、監査保存の失敗をロール変更の失敗として扱う点と、両者を同時確定する点は、合意した意図的な変更として扱う。APIの入力・出力・エラー形式は別途本家との互換性を確認する。

### 3.1 キャッシュへの変更通知

ロール変更と監査記録のcommit後に、キャッシュ無効化の通知を試みる。この通知のために「後続処理の依頼記録」は保存しない。通知に失敗しても、確定済みのロール変更を失敗と扱わず、通知を逃したキャッシュは有限の有効期限などで回復させる。

再起動したプロセスのメモリキャッシュは再作成されるが、他のプロセスやRedis上のキャッシュが消えるとは仮定しない。元データを再確認するまでの期限を維持し、通知を取り逃したキャッシュにも古さの上限を設ける。

Redisは必須基盤とし、通常の参照などで必要なRedis操作が失敗した場合はエラーとする。Redis障害時にDBへフォールバックする縮退運転は設けない。commit後の無効化通知の失敗は、前述のとおり確定済みの更新の失敗にはしない。

キャッシュ無効化以外の業務上必要な後続処理が加わる場合は、その仕事の保証を別に検討する。この通知を理由に、全変更イベントの永続化を必須にしない。

### 3.2 同じロールの並行更新と監査の変更前後

同じロールへの更新は、短いDBトランザクション内で順番に処理する。更新直前の状態の取得から、変更・監査記録の保存とcommitまで、同じロールへの別の更新が割り込まないようにする。具体的な排他方法は永続化アダプタで設計し、業務コードにDBのロックAPIを公開しない。

APIの更新単位に従って、指定された項目だけを変更する。監査記録には、トランザクション内で取得した実際の変更直前の状態と、保存した変更後の状態を残す。トランザクションより前に取得した古い状態を、監査上の変更前として使わない。

例えば、同じロールのドライブ容量が100MBの状態から、管理者Aが200MBへ、管理者Bが300MBへ変更する場合を考える。Aの変更の後にBの変更が成立したなら、Bの監査記録は「200→300」とし、「100→300」と記録しない。同じ項目への変更は、後から成立した更新を有効にする。

排他するのはDB更新中だけとし、管理者が画面を操作している間はロックを保持しない。画面で読み取った版をクライアントから送信させ、古い画面からの更新を競合エラーにする仕組みは、この初期方針では追加しない。既存APIを維持しつつ、更新と監査の整合性を守る。

### 3.3 ロール変更の認可

HTTP側の認証結果から実行者本人を特定し、ロール変更のUseCase側で管理者資格を判定する。この管理操作の認可では、判定に必要な永続化情報を更新トランザクション内でDBから取得し、共有キャッシュやプロセス内キャッシュの資格情報を根拠にしない。

今回の変更前の状態で認可し、許可された場合にロール変更と監査保存を行う。入力された変更によって実行者に与えられる資格を、その変更を許可する根拠にしない。rootユーザーなど、本家の管理者資格の規則も確認して維持する。

保証の境界は、このDB情報に基づく認可の判定時点とする。認可後に並行して起きた資格剥奪によって、進行中の操作まで必ず取り消す保証は求めず、認可済みの操作は完了し得る。この境界を超える厳密な直列化のための仕組みを、一律に追加しない。

## 4. 合意した成立条件の検証

- ロール変更の保存が失敗した場合、変更も監査記録も確定しない。
- 監査記録の保存が失敗した場合、ロール変更も確定しない。
- commitが成功した場合、ロール変更と対応する監査記録の両方が残る。
- ロール保存と監査保存が、同じトランザクションを利用していることを結合検証する。
- rollbackした変更の通知は発行しない。commit後の通知失敗だけを理由に、成立した変更を失敗と扱わない。
- 更新側のプロセスがcommit後・通知前に停止し、別プロセスのキャッシュが残る場合も、期限によって古い値から回復できることを検証する。
- 同じロールへの更新が並行した場合も、各監査記録の変更前後が実際に成立した更新の順序と一致する。
- 異なる項目への並行更新で、未指定の項目に対する他の更新を古い値で上書きしない。同じ項目は、後から成立した更新を有効にする。
- キャッシュに古い管理者資格が残っていても、更新トランザクションで取得したDB情報では資格がない実行者の変更を許可しない。
- 認可の判定にキャッシュを利用せず、今回の変更で新たに得る資格を、その変更自身の許可に使わない。
- 一つの評価境界の途中で失効時刻を跨いでも基準時刻を維持し、次の操作・再試行・明示的な再評価では新しい基準時刻を使う。
- commit後に自プロセスの該当キャッシュを無効化し、通知を受けた別プロセスも次の参照で変更を取得できる。
- 通知が欠落した場合も、保持期限後の次の参照ではDBから取得する。更新前に開始した読み取りの再投入で期限が延長されない。
- 取得中に無効化された値はキャッシュへ再登録せず、通知の購読再接続時にも対象のローカルキャッシュを破棄する。
- 自分の操作で計算材料を変更した場合は、その操作内の依存する評価結果も無効化する。

キャッシュ対象・保持期限・競合への対応は第6.2節に従う。検証の構成とCIの必須範囲は、基本方針の第14.1節に従う。

### 4.1 検証環境と互換性の期待値

純粋な評価処理とUseCaseの単体検証では、HTTPサーバー・DIコンテナを起動しない。DB・Redisの結合検証には実際のPostgreSQL・Redisを使う。HTTP検証では、第1.1節の対象APIについて、既存トークン認証、入力・出力・エラー、保存後のポリシー反映まで確認する。

本家比較は、基本方針の第16.2.1節で固定したコミットを基準に行う。初回と、追従で対象の契約が変わったときに新旧の実行結果を比較して期待値を確定し、通常のCIでは記録した期待値を使う。監査保存失敗時のrollbackなど、第3節の意図的な変更は別の期待値として明記する。

## 6. 操作内のメモ化

[本家PR #17823](https://github.com/misskey-dev/misskey/pull/17823)の、操作単位で取得・計算結果を再利用する考え方を採用する。同PRはHTTPリクエストや短いジョブなどごとにOperationContextを作る方式を提案している。調査対象のheadコミットは`d942c7110b06c53018396d43518e64e6dd1a1c89`。新バックエンドでの具体的な境界と公開契約は別途設計し、実装をそのまま移植することは前提にしない。

調査した実装では、同じtoken/keyに対する実行中のPromiseも保持して並行呼び出しをまとめ、ロール更新や割り当て変更後には対応するメモを無効化する。別の操作とはメモを共有しない。メモにはTTLを持たせず、操作の存続範囲で再利用する。

これは、ユーザーごとの評価結果をRedisなどで複数リクエストにまたがってキャッシュする方式とは区別する。複数操作で再利用する材料のメモリキャッシュと、操作内で取得・計算した結果のメモ化を併用する。

| 対象 | 方針 |
| --- | --- |
| ロール定義 | 全件をまとめてプロセス内のメモリキャッシュに保持する |
| 手動の割り当て情報 | ユーザー単位でプロセス内のメモリキャッシュに保持し、保持件数にも上限を設ける。割り当ての失効時刻は評価の基準時刻で確認する |
| ユーザー属性・基本ポリシー | 初期はDBから取得し、同じ操作内で再利用する |
| 実効ポリシーの計算結果 | 一つの業務操作内でメモ化する |
| 複数リクエストにまたがる計算結果 | 初期実装では保持せず、必要性が確認できてから検討する |

条件付きロールが参照するユーザー属性などの鮮度は、その情報を提供する領域の参照契約で定める。次の境界を満たすように詳細設計する。

- 同じ操作で同じ入力・参照条件の評価を繰り返す場合に再利用し、別の操作へ持ち越さない。
- キャッシュやメモを利用するかは、必要な鮮度と、今回の更新対象との関係で決める。トランザクションを開始したことだけを理由に、すべてのメモを一律に分離・破棄しない。
- 許容する古さの範囲にあり、今回の更新に影響されない情報は、トランザクション内でも通常参照のメモを再利用できる。判断に必要な時点のDB状態を要求する場合や、取得対象と更新対象が同じ場合は、そのトランザクションの状態に基づいて取得する。第3.3節の認可はこのDB参照が必要な用途とし、先にキャッシュから取得した資格情報を流用しない。
- 同じ操作中にロール、割り当て、条件付きロールが参照するユーザー属性などを変更した場合は、その変更に依存する結果も再評価する。取得対象自体が別でも、その計算材料を変更した場合を含める。共有キャッシュの無効化通知だけに、操作内の再評価を依存させない。
- キャッシュから取得した値と、そのトランザクションのDB状態に基づいて取得した値など、参照条件の異なる値を区別する。未commitの変更に依存するメモをトランザクション外へ持ち出さず、再試行にも引き継がない。操作内メモ化をDBトランザクションのスナップショットと同一視しない。
- 時間条件は第6.1節の基準時刻で評価する。長時間処理の別の評価境界や再試行へ、一つのメモを持ち越さない。
- 再利用する結果を、呼び出し元の変更によって他の読み取りへ影響させない。

メモ化は評価を呼び出す側の責務として設計し、業務上の純粋な評価関数にキャッシュ機構やAsyncLocalStorageを持ち込まない。新設計の実行コンテキストとの接続方法は、公開契約の詳細設計で決める。

### 6.1 評価の基準時刻

一つの業務判断の中では、時間条件を評価する基準時刻を固定する。

| 処理 | 基準時刻 |
| --- | --- |
| ジョブなどの遅延処理 | その実行試行の処理開始時刻。ジョブの登録日時は使わない |
| 1リクエストで一息に行う処理 | その処理で最初に評価した時刻 |

例えば、12時に失効する割り当てについて11時59分59秒を基準に評価した場合、同じ評価境界での再参照が12時を過ぎても、その基準時刻で判断を揃える。次のリクエストやジョブの再試行では、新しい基準時刻で評価する。

長時間処理では個別項目や処理段階などに評価境界を設け、各境界で基準時刻とメモを新しくする。実行直前の再確認が必要な操作も、その確認を明示的な評価境界として扱う。

同じ評価境界で依存する情報を変更した場合は、変更を反映して再評価する。その際も基準時刻は維持し、別の評価境界へ進む場合に新しい時刻を採る。時刻を固定することと、更新した情報を古いまま使うことは区別する。

基準時刻は純粋な評価関数へ明示的に渡す。これは業務上の期限や時間条件の評価に使う時刻であり、ログの発生時刻、タイムアウト、キャッシュの保持期限などの実際の時刻・経過時間の管理まで固定するものではない。

### 6.2 材料のキャッシュと変更反映の契約

初期は材料の値をプロセス内メモリへ保持し、Redisは無効化通知に使う。Redisにも同じ値を保持する二段構成は、必要になってから検討する。ロール更新の認可は、第3.3節に従いトランザクション内のDB情報で判断する。

変更反映と保持期限は、次の契約とする。

- commit後、自プロセスの該当キャッシュを無効化し、Redisで他プロセスにも通知する。無効化のための後続処理の依頼記録は保存しない。
- 通知を逃しても、保持期限を過ぎた次の参照ではDBから取得する。正常時は通知による反映を行い、通知欠落時の古さを保持期限で制限する。
- 保持期限はDB取得開始時から数え、キャッシュの参照や、古い読み取り結果の再投入で延長しない。
- 取得中に無効化された値は、キャッシュへ再登録しない。
- 通知の購読を再接続したときは、対象のローカルキャッシュを破棄する。
- 割り当ての失効はキャッシュ期限とは別に、第6.1節の基準時刻で確認する。
- 自分の操作で材料を更新した場合は、その操作内の依存する評価結果も無効化する。操作内メモの再利用・再評価の境界は第6節に従う。

保持期限の具体的な秒数は設定値として実装時に詰める。Redis障害時と、commit後の通知失敗時の扱いは第3.1節に従う。

## 7. 責務の分担

| 担当 | 責務 |
| --- | --- |
| ロール更新UseCase | 認可を行い、更新と監査を一つのトランザクションで成立させる |
| 実効ポリシー取得Service | 必要なロール・割り当て・ユーザー属性などを集め、評価結果を返す |
| 純粋な評価関数 | 取得済みの材料と基準時刻から、条件付きロールや実効ポリシーを計算する |
| 永続化アダプタ | DBからの取得、排他、保存、トランザクションを実装する |
| キャッシュ・通知アダプタ | キャッシュの保持・無効化と、commit後の変更通知を実装する |

「何を根拠に判定するか」と「その材料をどう取得するか」を分ける。管理者資格などの判定ルールを共有できる場合でも、通常参照でキャッシュを使う経路と、ロール更新の認可でトランザクション内のDB情報を使う経路では、それぞれが要求する参照条件を維持する。取得方法が異なることを理由に、同じ判定ロジックを二重に実装しない。

実効ポリシーの評価と管理者資格の判定を同一の処理にまとめることは求めない。それぞれの意味に合う評価関数を用意し、呼び出し元が取得済みの材料を渡す。

この分担は責務と公開契約の境界を定めるものであり、クラス数やファイル数を固定するものではない。キャッシュと通知も、それぞれの用途に合った契約を持ち、万能のRedisラッパーへまとめない。

### 7.1 更新UseCaseとトランザクションの契約

ロール更新UseCaseは、トランザクションを実行する業務側の契約へコールバックを渡す。基盤側はトランザクションを開始し、その接続に結び付いたRepositoryとDB参照の窓口をコールバックへ渡す。

`tx`として渡す束は、概念的には次の内容とする。名称と具体的な型は公開契約の詳細化で決める。

| 要素 | 想定する契約 | 責務 |
| --- | --- | --- |
| `roles` | RoleRepository | 更新対象のロールの取得・排他・保存 |
| `auditLogs` | ModerationLogRepository | 同じトランザクションでの監査記録の保存 |
| `authorizationFacts` | AdministratorFactsReader | 管理者資格の判定に必要な情報を、同じトランザクションのDBから取得する参照処理 |

これらは業務側が定義するインターフェースとし、TypeORMのRepositoryやEntityManagerをそのまま公開しない。認可用の参照処理は判断材料を返し、管理者かどうかの判断はUseCaseが呼ぶ純粋な評価処理で行う。業務Serviceを`tx`へ並べたり、全Repositoryを取り出せる万能コンテナにしたりしない。

UseCaseの実行メソッド全体が業務処理を所有する。認可、変更内容の決定、ロール保存、監査保存の順序と成立範囲は、UseCaseがコールバックの中身として定義する。基盤側は、その処理を同じDBトランザクションで成立させる役割を持ち、ロール変更に監査が必要かなどの業務判断を持たない。

基盤側はコールバックの正常終了後にcommitし、commitを確認してからトランザクション実行を正常完了させる。コールバック内の失敗は例外で伝え、基盤側はrollbackして失敗を外へ伝える。認可や対象ロールの存在確認などの業務上の失敗も例外で表し、失敗の戻り値を基盤側で例外へ変換する方式は採らない。HTTP・ワーカー側へのエラー変換は、そのトランザクションの外側で行う。commitの結果が不明な場合は第3節と基本方針の契約に従い、正常完了や確定したrollbackと同じ扱いにしない。

commit後のキャッシュ無効化通知は、UseCaseがトランザクション実行の正常完了後に依頼する。通知失敗によって確定済みの変更を失敗と扱わないことは、第3.1節に従う。

この束は同時確定させるDB操作に必要な能力に絞る。無関係なキャッシュ参照までこの束へ移すことは求めず、第6節の利用基準を維持する。渡されたトランザクション専用の窓口を、トランザクション終了後や別の仕事へ持ち出して利用しない。

### 7.2 最初のモジュール境界と公開契約

初期実装は、Role本体と、それを支える三つの能力に分ける。

| 担当 | 所有するもの・公開する能力 |
| --- | --- |
| Role | ロール定義・割り当て、取得・更新UseCase、条件評価、実効ポリシー取得、管理者・モデレーター資格の判定 |
| ユーザー情報の参照 | 条件評価に必要なアカウント状態、作成日時、フォロー数・投稿数などの属性を返す |
| インスタンス設定の参照 | 基本ポリシーやrootユーザーなど、判定に必要な設定を返す |
| 監査 | 実行者・操作内容・変更前後の記録を、呼び出し元のトランザクションで追記する |

ユーザー管理・インスタンス管理全体を初期実装の前提にせず、必要な参照能力だけを用意する。ユーザー情報・設定の参照側からRoleへ依存しない。監査側からRole更新を呼び出さず、更新に監査を伴わせる判断と成立範囲はRole更新UseCaseが所有する。

ロール更新は、HTTPでの認証後、Role更新UseCaseが第7.1節のトランザクション内で、認可用の情報取得、資格判定、Role更新、監査追記を行う。commit後にキャッシュ無効化通知を依頼する。

認可用の情報取得には、必要なテーブルをまとめて読む専用の参照処理を使ってよい。その参照処理は判断材料を返し、資格の判定自体はRole側の純粋な評価処理が行う。通常のキャッシュ付き参照と、更新トランザクション内のDB参照との鮮度の違いは維持する。

通常の実効ポリシー取得は、Role側の共通Serviceが、ロール・割り当て・ユーザー属性・基本ポリシーを集め、純粋な評価関数へ渡す。実効ポリシーの評価と管理者・モデレーター資格の判定は、それぞれの意味を保つ。

ロール取得APIに必要な割り当て人数などは、参照処理が取得してからレスポンスを組み立てる。レスポンス変換自体にはDBアクセスを持たせない。
