# Roleの純粋な評価処理と操作内メモ化

日付: 2026-10-17。対象: [#117](https://github.com/tiramiss-community/tiramiss/issues/117)。親: [#115](https://github.com/tiramiss-community/tiramiss/issues/115)、[全体計画 #114](https://github.com/tiramiss-community/tiramiss/issues/114)。

状態: 2026-10-17に本書の契約を会話で承認済み。[実装計画](../plans/2026-10-17-role-evaluation.md)に従って実装済み。単体検証の記録は[比較資料](../compatibility/role/README.md#117-評価処理と操作内メモの接続)を参照。HTTP・保存・共有キャッシュの接続は後続Issueの範囲。

前提: [基本設計](2026-10-15-misskey-backend-redesign-design.md)、[Role詳細設計](2026-10-16-role-policy-update-design.md)、[#116の互換性契約](2026-10-17-role-compatibility-contract.md)、[比較資料](../compatibility/role/README.md)。本家比較基準は `8e07cf085adf7009583d234a208e30436f020e26` を維持する。

## 1. 目的と範囲

取得済みの材料からRoleの実効ポリシーと資格を判定し、呼び出し側で同じ業務判断に必要な取得・計算を再利用する。自分の更新を反映し、参照条件や操作の違いによる値の混入を防ぐ。

今回の成果物は業務モデル、純粋な評価関数、材料取得のインターフェース、操作内メモとその単体テスト。HTTP・DI・DB・Redisなしで検証できる構成にする。HTTPへの接続は#120、更新・監査・認可のUseCaseは#118、複数操作で利用する材料キャッシュと通知は#119で実装する。

汎用のキャッシュフレームワーク、AsyncLocalStorage、永続ジョブ、確認用APIは追加しない。旧backendやそのビルド成果物へ依存しない。本家Entityの同期範囲も今回変更しない。

## 2. 採用する構成

Role向けの明示的な評価境界と、取得元に結び付いた参照セッションを採用する。純粋関数はその存在を知らず、値と基準時刻だけを受け取る。

汎用token/keyメモストアでは、Roleの材料と計算結果の依存関係が利用側へ散らばる。既存Serviceを移植する方式では取得方法と評価が混ざる。初期実装ではRoleに必要な取得・無効化を名前付きの契約に限定する。

配置は `packages/backend-next/src/modules/role/` を予定する。モデル、既定ポリシー、条件評価、適用ロール選択、ポリシー評価、資格評価、評価境界と取得処理を責務に応じて分ける。操作内メモのために他モジュール共通の実行コンテキストを先行実装しない。

## 3. 業務モデルと純粋関数

業務値は互換性契約§5の `UserRoleFacts`、`InstanceRoleFacts`、`RoleAssignment` に従う。評価に渡すロールはid、target、condFormula、policies、isAdministrator、isModeratorを持つ最小の投影とし、後続の保存モデルから渡せる構造にする。日時はミリ秒の数値を使い、Userの作成日時は参照アダプタがIDから復元する。

保存JSONと正常な評価結果の型を区別する。条件式・保存ポリシーは未検証JSONとして受け取り、型アサーションによって検証済みと見なさない。評価関数は入力を変更しない。

| 関数 | 入力と結果 |
| --- | --- |
| `evaluateCondition` | 保存条件式、ユーザー属性、有効な割り当てから得たロール、atMsからbooleanを返す |
| `selectApplicableRoles` | ロール定義、当該ユーザーの割り当て、ユーザー属性、atMsから適用ロールを返す |
| `evaluatePolicies` | 匿名かどうか、適用ロール、基本ポリシー、アップロード上限bytesから実効ポリシーを返す |
| `evaluatePrivileges` | userIdまたはnull、rootUserId、適用ロールから管理者・モデレーター資格を返す |

### 3.1 条件と割り当て

互換性契約§3をそのまま採用する。失効条件は `expiresAtMs <= atMs`。条件付きロールへの既存の手動割り当ても対象とする。`roleAssignedTo` は有効な割り当てで選ばれたロールだけを見る。条件一致の結果を次の条件へ連鎖させない。

空and、空or、作成日時の厳密不等号、全ユーザー属性・件数条件を維持する。未知の条件と評価中の例外は、その条件評価呼び出しでfalseとする。壊れた子条件をnotで囲むとtrueになり得る挙動も維持する。条件式の入力検証を強める仕様変更は加えない。

### 3.2 ポリシーと資格

互換性契約§4のキーごとの優先順位2→1→全候補、useDefaultの置換、型ごとの集約を維持する。匿名は基本値をそのまま返し、ログイン済みのロールなしは集約を通す。rootでもポリシーを特別値にしない。

実装に本家のコード既定値を定義し、比較資料の `policy-defaults.json` 全件との一致をテストする。実行時にdocsを読む依存は作らない。保存JSONの異常値を都合のよい正常値へ置換せず、固定コミットの該当処理と照合して扱いを確認する。追加調査が必要だった値は、実行確認かコード読解かを比較資料へ記録する。

資格は別関数で評価する。未認証は両資格false、rootは両資格true、管理者はモデレーターを兼ねる。HTTPでのサスペンド・scope拒否はここへ混ぜない。

## 4. 評価境界と参照セッション

### 4.1 基準時刻と寿命

呼び出し側が一つの業務判断ごとに評価境界を作り、明示的に渡す。リクエスト用は注入した時計から最初の評価時にatMsを一度だけ確定する。遅延処理用は試行開始時刻を作成時に指定する。時計の呼び出しは取得・メモ化側に限定し、純粋関数から現在時刻を読まない。

次のリクエスト・ジョブ再試行・長時間処理の次の段階・実行直前の再確認では、新しい評価境界を作る。同じ境界内の無効化はatMsを変えない。

境界には明示的な終了操作を設ける。終了後の参照を拒否し、保持する材料・Promise・評価結果を破棄する。呼び出し側は操作終了のfinallyで終了させる。HTTP・ワーカーへの実際の接続は後続Issueで行う。

### 4.2 材料取得の契約

取得窓口は次の能力だけを持つ。返す値は業務モデルであり、ORMやフレームワーク型を公開しない。

- 全ロールの取得。
- ユーザー単位の割り当て取得。
- ユーザー単位のRole用属性取得。不在は失敗として伝える。
- インスタンスのrootUserId・基本ポリシー取得。

通常参照セッションは#119のキャッシュ付き取得窓口を接続できる。#117のテストでは固定材料と遅延Promiseを返す窓口を使う。資格評価では基本ポリシーの集約をせず、実効ポリシー評価と必要な材料の取得を共有する。

### 4.3 参照条件とトランザクション

各セッションは作成時に取得窓口へ結び付ける。利用者が自由な文字列キーを指定して別の取得元を同じメモへ混ぜるAPIにはしない。同じ境界でも、通常のキャッシュ付き窓口とトランザクションのDB窓口は別セッションとする。異なるトランザクションも別セッションになる。

トランザクション内の認可では、そのトランザクションに結び付いたDB窓口のセッションを明示的に使う。通常参照で得た資格を流用しない。評価境界は共有できるためatMsは同じとし、材料・結果は参照条件ごとに分ける。

トランザクションを開始しただけで既存の通常参照メモを全破棄しない。更新に影響されず古さを許容できる情報は、呼び出し側が通常参照セッションから明示的に再利用できる。今回の更新対象・依存材料や認可をその対象にしない。

トランザクションのセッションはコールバック内で作成し、そのfinallyで終了する。取得中に終了した場合も、終了後に完了した値を公開・再登録しない。評価結果を通常参照セッションへ移すAPIは設けない。既存 `TransactionRunner` 自体の変更は今回不要で、#118がこの寿命管理を接続する。

## 5. メモ化と更新反映

同じセッションで同じユーザー・同じ材料を並行要求した場合は、実行中のPromiseを共有する。匿名とユーザーは別入力とし、ユーザー間でも材料・結果を混ぜない。失敗を成功値へ変換せず、失敗したメモは取り除いて、次の明示的な参照で再取得できるようにする。失敗した古いPromiseが、無効化後に登録した新しいメモを削除しないようにする。

取得値は受け取った時点で所有するコピーを保持し、外へ返す値もコピーする。取得元や呼び出し元の配列・保存JSON変更で、他の読み取り結果が変わらないようにする。

### 5.1 依存関係

| 変更した材料 | 無効化するもの |
| --- | --- |
| ロール定義 | 全ユーザーの適用ロール・実効ポリシー・資格とロール材料 |
| あるユーザーの割り当て | そのユーザーの割り当て・適用ロール・実効ポリシー・資格 |
| あるユーザーの属性 | そのユーザーの属性・適用ロール・実効ポリシー・資格 |
| インスタンス設定 | 設定材料、全ユーザーと匿名の実効ポリシー・資格 |

明示的な無効化操作を評価境界に用意し、配下の全参照セッションへ適用する。無関係なユーザー属性・割り当てまで取得し直さない。ロール定義の変更は、変更前に適用されていなかったロールも条件・ポリシー・資格を変え得るため、該当roleIdを過去に利用したユーザーだけへ絞らない。

トランザクション内で材料を変更して再評価するときは、その変更後に無効化する。通常参照で未commit値を取得してよいという意味にはならず、更新に依存する判断は引き続きトランザクションのセッションを使う。commit後は通常参照の材料キャッシュも無効化する。この接続順序は#118・#119が所有する。rollback・終了したセッションの材料は再利用しない。

### 5.2 取得中・計算中の無効化

材料と計算結果の登録には依存する材料の世代を結び付ける。無効化時には、実行中のメモを含めて該当世代を進める。古い取得が遅れて完了しても、新世代のメモとして登録しない。

取得開始時と完了時で必要な世代が変わっていた場合、待機中の呼び出しには明示的な `EvaluationInvalidated` を返し、古い値を正常な評価結果にしない。内部で無制限の再取得はしない。呼び出し側は必要に応じて同じ境界・同じatMsで改めて評価する。この例外は業務判断の拒否・DBトランザクションの再試行要求ではなく、判断材料の取得中に自操作が変更したことを示す。後続の呼び出し側は未完了の評価を更新後に成功した評価として使わない。

終了後に完了した取得は、セッション終了を表す失敗とする。終了前に正常完了して呼び出し元へ渡った値まで回収する保証は持たない。更新後の判断では再評価を呼ぶ。

## 6. 検証と完了条件

純粋関数のテストは本家unit probeの入力・assertionを新しい公開契約へ対応付ける。本家ServiceやNestJSをimportしない。既定ポリシーの期待値は共通JSONを読み、テスト内へ別の定数として複製しない。

追加で次を確認する。

- 条件全種類、壊れた子条件、割り当ての期限前・一致・期限後、条件付きロールの非連鎖と既存割り当て。
- 全既定値、優先順位・基本値・型ごとの集約、匿名とログイン済みの差、rootと資格の独立性。
- 初回評価時刻の固定、試行開始時刻、無効化後も同じ時刻、次の操作・再試行では新しい境界。
- 同条件の並行取得の集約、別ユーザー・別参照セッション・別操作の分離、失敗後の再取得。
- 材料ごとの依存結果の無効化と無関係な材料の再利用、古いPromiseの遅い成功・失敗による再投入防止。
- 通常参照とトランザクション内参照の分離、セッション終了後の参照拒否、取得中に終了した値の非公開。
- 返した値と取得元の値を変更しても、他の読み取り結果に影響しないこと。

対象のunit test、依存順ビルド・型検査を実行する。DB・Redisアダプタを変更しないため今回の検証に実DBは必要としない。共通チェックはshipping-misskey-changeに従い、変更TSのESLint・SPDX・locale safetyを実行する。

比較資料の引き継ぎ表へ、新実装に接続したテスト・コマンド・結果を記録する。HTTP・永続化・共有キャッシュの新旧一致や#115全体の完了とは扱わない。

## 7. 後続への引き継ぎ

#118はトランザクションの認可材料を資格評価へ渡し、更新時の操作内無効化・終了を接続する。#119は通常参照窓口へ材料キャッシュを実装し、commit後のローカル無効化・Redis通知を接続する。#120はリクエストの評価境界の作成・終了とHTTP認証を接続する。

この実装でRole評価と操作内メモの契約を揃えた後、#118と#119へ進める。共有キャッシュのTTL・件数制限、認可と保存の同時確定、HTTPの応答互換性は各後続Issueで検証する。
