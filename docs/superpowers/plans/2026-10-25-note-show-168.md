# 投稿 N1 notes/show Implementation Plan

> **For agentic workers:** Use superpowers:executing-plans to implement this plan task-by-task, then request an independent review.

**Goal:** #168 の notes/show を既存の本家データから提供する。

**Architecture:** 合意済み[投稿設計 §5](../specs/2026-10-21-note-flow-design.md)を実行する。UseCase が root のエラー判定と取得計画を所有し、階層ごとに未取得 Note を集合取得する。永続化adapterは本家Entityを業務factsへ変換し、取得済みfactsだけから純粋に出力する。

**Tech Stack:** TypeScript / Hono / TypeORM / PostgreSQL / Redis / Vitest。

**Spec:** ../specs/2026-10-21-note-flow-design.md、../compatibility/note/README.md。

## Global Constraints

- 本家SHA `8e07cf085adf7009583d234a208e30436f020e26` を維持。Entityはmanifestとsync経由だけで追加する。
- 通常CRUDはRepository/QueryBuilderを使う。業務へEntityやHono Contextを渡さない。
- replyはdetail:false、renoteはdetail:true。hiddenのnull/省略とネストの挙動を保持する。
- 参照中のミュート・ブロックを独自の拒否条件にしない。scopeなし・停止/移行actorも本家show同様に扱う。
- 深い参照は最大64階層・256 Noteを上限に、循環/予算超過を記録して500とする。これは破損/過大データに対する有限化であり本家と同じ上限の主張ではない。
- notes/create/delete、一覧、変更API、AP/通知/worker接続は後続Issue。

## Review Focus

- hidden rootの内部reply/renoteが独立に表示判定されることと、detail:false replyでは返信先例外の材料が無いこと。
- 同じNoteがreply/detail:falseとrenote/detail:true双方で現れても詳細取得を欠かさず、共有参照を循環と誤認しないこと。
- reaction DB/cache/bufferと2秒境界、0値・legacy custom emojiを保つこと。
- 作者の時刻制限・guest server local/noneの順序、本人例外、添付欠落の順序を保つこと。
- Token不正・Bearer優先・App/native・schemaエラー・GET405を既存HTTP入口と照合すること。
