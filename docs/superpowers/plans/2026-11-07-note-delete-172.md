# Note deletion (#172) implementation plan

> **For agentic workers:** Use superpowers:executing-plans in the existing isolated worktree. No commits or external updates in this execution.

**Goal:** Connect the supported notes/delete HTTP path, deletion persistence and author-signed Delete/Undo delivery.

**Architecture:** A plain deletion UseCase owns authorization, preparation and deletion. TypeORM reads the pre-deletion note and concerned remote users; pure federation functions render the activity. Separate followers, relay and concerned-user branches use the existing queues and a tracked background task participates in shutdown draining.

**Tech Stack:** Existing TypeScript, Hono, TypeORM, BullMQ, PostgreSQL, Redis and Vitest. No dependencies or schema changes.

**Spec:** [GOALS](../../backend-next/GOALS.md), [posting contract](../../backend-next/posting-contract.md), [issue #172](https://github.com/tiramiss-community/tiramiss/issues/172), fixed upstream `8e07cf085adf7009583d234a208e30436f020e26` notes/delete, NoteDeleteService and ApRendererService.

## Scope and approach

Use the existing supported Note rows, authentication and ordinary deliver worker. Reusing create delivery would change deletion audiences; introducing a durable deletion record would add a deferred guarantee. The selected path captures only the materials needed during this operation and retains the original author for HTTP/LD signatures. Deletion stream/notification, TL/search, webhook and charts remain #173–#176/#200. Remote actor resolution remains #195.

## Global constraints

- Base `a74413b55d`; preserve unrelated original-checkout changes.
- Do not edit old backend, synchronized upstream files, existing migrations, CHANGELOG or locale files.
- No transactions across external delivery or producer retry, snapshot tables, cancellation generations or stronger Create/Delete ordering.
- Match upstream's independent followers/relay/direct branches, including nonpublic deletion and no cross-branch sharedInbox deduplication.
- Only reply-parent repliesCount is decremented. User, renote and channel counters remain unchanged.
- Current moderator authorization comes from current DB role facts; moved users may delete. Scope is write:notes; production limits are 300/hour and minimum 1 second, modified by role factor.
- Preserve upstream failure boundaries: reply decrement precedes deletion and is not rolled back by a failed DELETE; audit and producer failures are observed background failures, not local deletion rollback.

## Review focus

1. Nonpublic deletion and concerned remote users must not be filtered by creation audience rules.
2. Pure Renote includes CW, reply, files and poll checks; original disappearance uses Delete fallback.
3. Moderator deletes sign as the original author and retain full pre-delete audit data.
4. Reply decrement and deletion failure are separate statements, while failed background work must be logged and drained.
5. Authentication/rate/suspension/scope/input precedence, moved users and fresh moderator roles must match fixed upstream.
