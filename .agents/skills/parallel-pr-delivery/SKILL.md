# 並行PR作業

## 総括が着手対象を選ぶ

総括は親Issueの目的・完了条件・先行依存を読み、候補の子Issue、open PR、統合先に入った成果を照合する。着手できる部分と完了に必要な依存を区別し、後続を解放する作業と独立して進められる作業を選ぶ。共有コード・台帳・生成物の編集者を決める。独立PRは同じ統合先を基点とし、stackが必要なら依存理由を示す。

## 工程に合わせて担当を起動する

| 担当定義 | 配置と推論強度 |
| --- | --- |
| [総括](../../../.codex/agents/delivery_coordinator.toml) | 全体で1人、Astra 6.2 medium。親が担当できれば兼任する。 |
| [リーダー](../../../.codex/agents/delivery_lead.toml) | Issueごとに1人、Sol 6.2 high。仕様や互換性の難しい判断にはxhighを選べる。 |
| [実装](../../../.codex/agents/delivery_implementer.toml) | Issueごとに1人から開始、Sol 6.2 medium。定型変更はlow、複数層の原因調査はhigh。編集・検証範囲を分離できる場合に増員する。 |
| [独立レビュー](../../../.codex/agents/delivery_reviewer.toml) | Issueごとに1人、Sol 6.2 high。検証可能な差分ができたら起動する。 |
| [CI・CodeRabbit監視](../../../.codex/agents/delivery_monitor.toml) | PRごとに窓口を1人決め、複数PRを兼務できる。Terra 6.1 medium、複雑な失敗の切り分けはhigh。 |

利用者の指定を優先する。実際の並列枠に合わせて工程をずらし、待機役の常駐で実装・再レビューを塞がない。ネストした委任ができない環境では、総括がリーダーの指示を対象の担当へ渡す。名前付き担当が使えない場合は対応するTOMLの指示とモデル・推論強度で起動し、利用できないモデルは明示する。

リーダーは背景・先行成果・対象外・検収条件・必要な証拠を一度まとめ、実装者には編集範囲、レビュー担当には独立して確かめる契約を添える。修正の採否と成果物の検収を担い、総括へは依存衝突・判断待ち・完了など他Issueの進行を変える事実を返す。

### Ultracodeを使う判断

総括・リーダー・実装・レビューは、並行して答えられる具体的な問いがあるときに利用できる。総括ならIssue間の依存調査、リーダーなら先行実装と検収根拠の調査、実装者なら複数入口の影響調査、レビュー担当なら互換性と失敗時の副作用の独立検証が候補になる。単独で判断できる変更はそのまま進める。

総括が利用可能な並行数・予算を配分し、リーダーがIssue内の実行を調整する。同じIssueでは原則同時に1実行とし、総括の横断調査とも対象を照合する。各担当は配分内で問い・終了条件を決め、結果と根拠を引き継ぐ。実装の書き込みを分ける場合はリーダーが所有範囲を割り当てる。

## 作業環境

- 作業は専用worktreeへ隔離する。共有node_modulesへのsymlinkを介したinstall/rebuildは隔離ではない。実DB等のプロジェクト名・ポート・片付けの所有者を分ける。

## 小さい引き継ぎで実装する

子への入力は、対象Issueと完了条件、基点/worktree、編集範囲、固定比較元、必要な規約、既知の制約と検証コマンドに絞る。対応するツールではfork_turns=noneを使い、会話全体や巨大なログを渡さない。

実装前に通常の製品入口が完了条件を満たすか、比較元が実際のimport先かを確認する。テストfixtureだけで成立する保証を通常起動の保証に読み替えない。新しい観測のIDは一意にし、入力と結果を1対1で照合する。

報告は「変更/検証結果/未解決/次の判断/成果物のパス」に絞る。全ログはファイルに保存し、親には失敗箇所と必要な周辺だけ渡す。同じ事実を複数担当が報告し直さない。

## 比較記録の保守を分離する

必要な場合だけ、プロジェクトエージェント `evidence_inventory`（Luna）または `evidence_maintainer`（Terra）を使う。定義は現在のworktreeの [evidence_inventory](../../../.codex/agents/evidence_inventory.toml) と [evidence_maintainer](../../../.codex/agents/evidence_maintainer.toml) にある。個人用の同名定義より、このworktree内の定義を参照する。利用クライアントが名前付きエージェントを扱えない場合は、該当TOMLのmodel・reasoning・developer_instructionsを明示して通常の子として起動する。利用できないモデルを黙って置換しない。

小さな更新なら実装担当が行い、調査→保守の2人を毎回起動しない。調査はread-only、保守は指定ファイルだけ。次は取りまとめ役へ戻す:

- 本家との差・完了条件・意図的差異の新しい判断
- validatorの保証、readerの合成、memoization/invalidationの変更
- 検証上限の変更や複数領域へ広がる修正

古い測定値を現在の実装へ付け替えない。hash更新は再測定の代わりにならない。実測入力と後続の記録更新を区別する。

## 独立レビューと検証

- 実装者以外のレビューを必須にする。通常入口・本家参照・失敗境界・証拠の対応を確認する。
- 修正後は変更箇所と影響範囲を再レビューする。無関係な全体レビューを再開しない。基盤契約に波及する変更なら範囲を広げる理由を示す。
- 変更に近いテストとリポジトリ必須チェックを実行する。同じheadの成功を理由なく繰り返さない。新しい変更・失敗・具体的な懸念があるときに追加する。
- 先行PRの契約に依存する場合は、先行headの更新後に後続の基点を照合し、影響する契約を組み合わせて検証する。複数PRが共通ファイルを触る場合は最終head同士の競合と必要な合成検証を一度確認する。FAILやSKIPを成功に混ぜない。

## PRと監視の終了条件

PR作成・push・外部送信は現在の依頼が許可する範囲だけ。スキル自体は送信権限を与えない。merge/close/force-pushの権限も追加しない。

CI失敗時は対象head・jobを記録する。一時的なrunner障害ならリーダーが許可範囲内で再実行担当を1人決め、同じ失敗が続いたら原因調査へ戻す。

監視担当は新規指摘を対象PR・commit・スレッドとともにリーダーへ渡す。採否と修正をリーダーが確認し、利用者から返信の許可がある場合は監視担当が元スレッドへ修正commit・検証結果または対応を見送る根拠を返す。CIは最新head、Webレビューは対象commit・未解決指摘・処理中の有無を追跡する。通知が使えるなら利用し、なければCIは間隔を置いて確認する。レート制限は次の依頼可能時刻を記録し、解除前に繰り返し送信しない。待機中の新規サブエージェントや調査を増やさない。報告は状態変化中心とし、上位指示が定期報告を要求する場合は短くまとめる。

通常の完了条件:

1. 独立レビュー済みで、最新CIが成功している。
2. 依頼されたWebレビューが一度完了し、指摘を検証して修正または対応を見送る根拠を確認した。返信権限がない場合は根拠と未返信スレッドを利用者に引き継ぐ。返信自体が必須の依頼なら権限待ちとして示す。修正差分は独立確認し、必要な最新検証を通した。
3. 既知の未解決事項・実際に進行中のレビューへ対応した。

修正後すべての差分にWeb再レビューや正式APPROVEDを要求する条件を勝手に追加しない。利用者やリポジトリが要求する場合は従う。追加のWeb再レビューが制限中なら、その事実と実際の確認範囲を明記する。旧CHANGES_REQUESTED表示を承認済みと呼ばない。初回Webレビューが未到達なら完了とは扱わず、許可範囲で待機を続けるか利用者へ阻害要因を伝える。

引き継ぎはPR、変更の目的、最新検証、レビュー状況、残る制限を短く示す。
